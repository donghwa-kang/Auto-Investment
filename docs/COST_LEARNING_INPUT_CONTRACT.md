# V3 학습 입력 사전 계약과 HOLD 수용 조건 — D3

_2026-09-24 · DEV-D03 내부 설계 인수. 후속 D4 읽기 전용 진단기는 구현했으나 제품 변환기·새 학습 형식의 구현 완료나 운영비 정책 승인은 아니다._

---

## 📋 결정과 적용 범위

현재 [D2 파일 검증](COST_OUTCOME_EXPORT.md)의 성공은 **비용 근거가 재생과 일치한다는 뜻**이지 학습 가능한 표본이 완성됐다는 뜻이 아니다. 다음 구현은 학습 변환이 아니라 **검증된 자료의 준비도 진단**으로 한정한다. 학습 입력·라벨은 만들지 않고 HOLD의 구체적인 원인을 보여준다.

| 선택 | 판단 | 이유 |
| --- | --- | --- |
| V3 값을 구형 학습 형식에 끼워 넣기 | 제외 | 거래소 비용 분리 필드·새 원천 결합이 없고, 특징 원자료·운영비 확정도 미연결 |
| 운영비와 특징을 기본값으로 채워 바로 학습 | 제외 | 합성 무운영비와 실제 비용 미확인, 선언 특징과 당시 원자료를 혼동 |
| D2를 검증한 뒤 읽기 전용 준비도 보고 | 다음 구현 범위 | 확인 가능한 금융 사실은 보존하고, 부족한 계약과 자료를 개별 표시 |

D3에서 고정하는 것은 이 엔지니어링 경계와 후속 인수 조건이다. 원본 거래 전략·손실 한도·R0·TTL·운영비 미결정 `OC-U01`~`OC-U08`을 변경하지 않는다. 구형 학습기, V1/V2/V3 원장, D1/D2 형식·해시도 변경하지 않는다. 실제 자료 수집·API 키·유료 AI·계좌·주문·자동 학습·모델 교체는 범위 밖이다.

D3 당시 산출물은 명세와 기존 동작 대조였다. 이후 아래 고정 D4 계약을 [읽기 전용 준비도 진단기](COST_LEARNING_READINESS.md)로 구현했다. 후속 실제 학습 계약은 여전히 미구현이며 D3의 운영비 미결정 사항을 바꾸지 않았다.

## 🔐 수용 판정은 세 가지로 분리

1. **자료 거절:** D2의 형식·기준 해시·원본 정책·재생·영수증·보고 대조 실패. 준비도 보고나 부분 학습 자료를 만들지 않는다. 실패 자료를 수정하거나 원장을 복구하지 않는다.
2. **금융 근거 수용 / 학습 HOLD:** D2 검증은 통과했지만 아직 미완료·특징 미연결·운영비 미확정 등이다. 확인된 원통화 손익과 비용을 보존한다. 현재 모든 V3 입력은 여기에 머문다.
3. **향후 학습 입력 적격:** 새 버전 특징·라벨·운영비·중복/시간 분할 계약을 구현하고 인수한 뒤의 별도 단계다. D3/D4는 이 상태를 출력하거나 활성화하지 않는다.

미결제, FX 공백, 거래 중지 래치, 모델 사용 권한은 서로 다른 사실이다. 미결제 매도대금을 재매수 예산으로 만들지 않지만, 결제를 기다린다는 이유로 확정 매매손익을 지우지도 않는다. 위험 중지나 음수 손익이 있다는 이유만으로 기록을 버리면 안 된다. 반대로 이 기록을 보존한다는 이유로 거래 중지 래치를 해제하거나 학습 허용으로 승격하지 않는다.

기준은 파일에서 자동 추출하지 않는다. 신뢰 `OutcomeConfig`와 별도 보관한 `exportHash`로 D2를 재검증한다. D2의 최대 16MiB·깊이64·노드500,000·명령5,200 및 로컬 파일 경계를 유지하며 상한 초과를 부분 절삭으로 통과시키지 않는다. 이 기준도 서명·출처 인증·최신성·OS 격리의 대체물이 아니다.

## 📊 후속 학습 계약에서 보존할 의미

### 금융 필드와 이중 차감 방지

| 필드·근거 | 보존/재계산 원칙 | 금지되는 대체 |
| --- | --- | --- |
| `postings[].fill` | 체결 ID·발생/수신시각·seq·수량·가격 그대로 | 동시각에 임의 1ms 추가, 체결 합치기 |
| `components` | COMMISSION/TAX/EXCHANGE 각각 `amountDelta` 합 | ORDER 누계 반복 합산, 전부 commission으로 분류 |
| `tradingFees` | 위 세 항목 합과 일치 | 예약금을 실제 비용으로 추가 |
| 거래 손익 | 닫힌 거래의 `sellValue - buyValue - tradingFees`와 종료 결과 대조 | 이미 비용을 뺀 net에서 거래비를 다시 차감 |
| 체결 오차·스프레드 | 실제 체결 가격에 포함된 영향은 별도 분석 가능 | 같은 가격 손실을 slippage 비용으로 다시 차감 |
| 미수/미지급·결제 | 금융 상태를 보존하되 결제는 손익 재인식이 아님 | 미수금을 현금으로 사용, SETTLE마다 표본 추가 |
| 운영비 | 확정 배분 근거가 연결되기 전 `null`/HOLD | 후보 `operatingEstimateKrw`·미확인 비용을 확정 라벨의 0원으로 사용 |
| FX | 원통화 결과와 확인된 종료 원화 결과를 따로 보존 | USD와 KRW 직접 합산, 현재 환율로 과거 손익 재작성 |

허용된 실제 환전 사건이 없으면 환전 비용을 만들어 내지 않는다. 반대로 계약이 아직 지원되지 않는 비용을 ‘실제 0원’으로 단정하지 않는다. FX 비용·DAY 과금 등 현재 실행기가 미지원인 범위는 새 입력 버전과 별도 인수 전까지 확대하지 않는다.

후속 전체 비용 라벨은 확정 거래비와 확정 운영비 배분을 같은 통화에서 한 번만 차감해야 한다. KRW 배분액을 USD 손익에서 그대로 빼거나 임의 환율로 변환하지 않는다. 운영비 배분은 설명용 귀속이지 공용 장부에 새 비용을 인식하는 사건이 아니다.

### 위험 단위와 특징의 시점

기존 구형 변환의 분모는 **승인 당시 계획 수량 × (계획 진입가 − 계획 보호가)**인 원통화 가격 위험이다. 후속 V3 연결에서도 원본 승인 근거로 재구성해야 하며, `candidate.budgetKrw`나 종료 결과의 `initialBudgetKrw`를 이 분모로 쓰지 않는다. 이 값들은 허용 예산이지 가격 위험 자체가 아니다. 비용 포함 예약 위험도 분모를 대신하지 않는다.

계획 3주 중 2주만 체결돼 종료했더라도 미래의 실제 수량으로 계획 위험을 다시 쓰지 않는다. 통화와 기준 시점·수량·가격·보호가·승인 해시를 함께 명시한다. 원통화 분모와 원화 손익을 혼용하지 않고 표현 범위 초과·0 이하 분모는 보류한다. D4 진단기는 이 계산을 새 `netR`/학습 정답으로 출력하지 않는다.

특징에는 실제 판단의 ID, 전략/숫자 계산 버전, 원천 시각·가용시각·원자료 해시, 지표 재계산 근거가 필요하다. `sourceAsOf ≤ featureAvailableAt ≤ decisionAt`을 충족해야 하며 승인 요청에 적힌 값만으로 원자료를 확인했다고 하지 않는다. 청산 가격·종료 손익·미래 환율·미래 시나리오 기대값·나중 운영비를 판단 당시 특징에 넣지 않는다. 승인 시각을 원래 전략 판단 시각으로 무조건 대신하지 않는다.

### 라벨의 가용시각과 기간

미래 라벨의 가용시각은 최종 청산/주문 종결 근거, 비용 확정·배분, 필요한 환산/정정 근거를 **모두 사용할 수 있었던 시각 이상**이어야 한다. `closedAt` 하나로 비용 배분이 끝났다고 간주하지 않는다. 저장한 문서의 시각이나 가용시각 선언만으로 원천 증거를 대신하지 않는다.

향후 학습 분할은 당시 사용 가능했던 판본을 재구성하고, 판단·청산·라벨 가용시각이 학습 구간 끝보다 엄격히 앞서는 기존 경계를 보존한다. 시간 embargo·검증 구간·표본 수는 원래 계약을 따르며 새 임의 수치를 만들지 않는다. 동일 진입 의도의 스냅샷·정정판을 학습/검증 양쪽에 중복 배치하지 않는다. 늦은 비용/정정의 실제 지원은 OC-U05~07 결정과 새 버전의 인수 전까지 보류한다.

### ID·포함 범위·선택 편향

현재 보장 가능한 범위는 **해당 V3 실행의 확정 승인 전체**다. 미인계·해제·무체결·미완료·손실·FX 미확정 기록을 삭제하지 않는다. 승인 전 거절 후보·당시 전체 유니버스·뉴스/공시 판단을 이 원장이 담았다고 표시하지 않는다. 무체결을 0원 수익 표본으로 만들거나 거절 후보에 가상 체결 정답을 붙이지 않는다.

자료셋을 나중에 구성할 때 `exportHash`나 `financialBasisHash`를 거래 ID로 삼으면 SETTLE/관측 때마다 같은 거래가 늘어난다. 안정된 원천 실행·진입 의도 ID와 스냅샷 해시를 구별해야 한다. 여러 스냅샷을 합산하지 않고 동일 의도의 당시 유효한 판본 하나를 선택한다. 서로 다른 합성 실행의 경제적 중복·동일 시장 구간 중복은 별도 자료셋 계보 검사 대상이며, 해시가 다르다고 독립 표본인 것은 아니다.

## ⚙️ D4 준비도 진단기 계약 — 읽기 전용 구현

개발자 함수 `assessCostLearningReadiness(text, anchor)`와 전용 시험을 D4에 구현했다. 이 이름과 아래 반환 형식은 D3에서 정한 계약이며 [현재 사용법](COST_LEARNING_READINESS.md)을 따른다. 입력은 원래 D2 JSON 문자열과 `CostExportAnchor`만 받는다. 별도 운영비/특징 덮어쓰기 인자나 `allowTraining` 우회 옵션은 두지 않는다. DB/파일 쓰기는 없지만 기존 D2의 정책 파일 읽기 검사는 재사용한다.

내부에서 기존 `verifyCostOutcomeExport`를 반드시 호출하고 **재생으로 돌려받은 보고**를 사용한다. 파일의 `verified:true` 표시나 호출자가 만든 구조적 ‘검증 완료 객체’만 믿지 않는다. DB·파일 쓰기·HTTP·학습 실행·등록·모델 교체 함수를 호출하지 않는다. 파일 입력은 기존 로컬 읽기 경계의 후속 연결로 따로 다루며 D4에 새 CLI/UI를 만들지 않는다.

| 출력 | 계약 |
| --- | --- |
| `kind`, `purpose`, `status` | `COST_LEARNING_READINESS_V1`, `TEST_ONLY`, `HOLD` 고정 |
| `source` | D2 exportHash + D1 source/config/policy/state/revision/epoch/asOf 및 financialBasisHash/reportHash |
| `financialReport` | D2가 재생한 D1 보고를 분리 사본으로 보존 |
| `coverage` | `scope=PERSISTED_APPROVALS_ONLY`, 승인 수/인계 수/phase별 수, `preApprovalDecisions=NOT_RECORDED_BY_V3_CONTRACT` |
| 최상위 `checks` | 승인 0개를 포함한 모든 유효 입력에 아래 고정 5개 진단을 표 순서대로 포함 |
| `records` | 모든 승인에 정확히 한 행. 입력 승인 순서 유지. 거래가 없으면 runId/outcomeBasisHash는 null |
| 행 식별 | `rowId=hash({configHash, sourceScope: anchor.config.sourceScope, reservationId})`; basis 해시와 별도. 같은 V3 실행의 SETTLE 전후 안정성이지 다른 실행 전체의 중복 판정은 아님 |
| 행 phase | 미인계는 원래 `RESERVED_LOCAL`/`RELEASED_LOCAL`; 인계 후는 D1의 `NO_FILLS`/`INCOMPLETE_TRADE`/`CLOSED` |
| 행 근거 | reservationId, runId, currency, approvalBasisHash, outcomeBasisHash, financialBasisHash, 원래 D1 HOLD 사유와 상태 |
| 행 `status`, `checks` | `status=HOLD` 고정. 최상위 고정 5개 진단의 분리 사본. 평가 불가를 PASS나 0원으로 바꾸지 않음 |
| 라벨·허용 | 각 행 `trainingLabel=null`; 전체 `trainingInput=null`, `learningAllowed=false`, `orderSubmissionAllowed=false`, `liveEnabled=false` |
| 결과 해시 | `readinessHash=hash(반환 본문에서 readinessHash만 제외)`; 변경 탐지용이며 인증/학습 허가 아님 |

후속 진단 코드들은 D1의 원래 사유를 지우거나 그 의미를 덮어쓰지 않는다. 아래는 새 진단기의 고정 체크 계약이다. 기존 V3 자료만 받으므로 누락 원천을 외부에서 채워 PASS로 승격할 경로가 없다.

| 체크 ID | D4의 상태·사유 | 뜻 |
| --- | --- | --- |
| `FINANCIAL_REPLAY` | `VERIFIED` | D2를 통한 금융 근거 일치. 학습 가능하다는 뜻 아님 |
| `FEATURE_BINDING` | `MISSING`, `V3_FEATURE_SOURCE_NOT_BOUND` | V3 판단과 재구성 특징 원천의 계약 미연결 |
| `OPERATING_ALLOCATION` | `UNSUPPORTED`, 기존 `OPERATING_COST_ALLOCATION_UNSUPPORTED` | 배분/확정 비용 미지원 |
| `TRAINING_CONTRACT` | `UNSUPPORTED`, 기존 `V3_TRAINING_CONTRACT_NOT_INTEGRATED` | 새 학습기 입력과 라벨 결합 미구현 |
| `POPULATION_SCOPE` | `LIMITED`, `V3_PREAPPROVAL_POPULATION_NOT_RECORDED` | 확정 승인 외 시장/거절 후보 모집단 없음 |

각 체크는 `{ id, status, reasons }` 형태다. `reasons`는 항상 문자열 배열이며 `FINANCIAL_REPLAY`는 `[]`, 나머지 네 항목은 위 표의 사유 코드 하나씩을 담는다. 최상위 `checks`는 `records=[]`여도 고정 5개를 보존한다. 각 행에도 같은 내용의 분리 사본을 두어 한 배열을 수정해 다른 행이나 최상위 결과가 바뀌지 않게 한다. phase·결제·FX·위험 중지 여부는 원래 금융 보고에서 보존하며, 별도 `READY` 상태를 만들지 않는다. 0행도 HOLD 보고로 반환하고 학습 표본 수는 0이다. 목적은 어떤 계약이 비어 있는지 드러내는 것으로, 임의 합성 가격·특징을 생성하는 것이 아니다.

```powershell
node --test --test-concurrency=1 dist/runtime/tests/cost-outcome-export.test.js dist/runtime/tests/learning-bridge.test.js dist/runtime/tests/learning-rvol-bridge.test.js dist/runtime/tests/operating-allocation.test.js dist/runtime/tests/operating-journal.test.js dist/runtime/tests/learning.test.js

```

실행 결과·문서 표시·파일 보존·미실행 항목은 [PROGRESS · 공개 요약](PROJECT_STATUS.md)를 따른다. 기존 전체 1,627개 회귀 통과는 D2 시점의 기록이며 D3에서 전체를 재실행했다고 하지 않는다. 실제 시장 데이터/수익성, V3 모델 학습, 실제 운영비 정책·정산, 최대 부하·OS 격리는 검증하지 않는다.
