## 제공 범위와 실행

새 [체결 원장](../src/core/cost-execution.ts)은 [비용 계산기](TRANSACTION_COST_LAB.md)를 재사용한다. 한 합성 종목·한 통화의 매수 1회와 보유 잔량 전체를 대상으로 하는 매도 취소/대체 체인에서, 실제로 입력된 개별 체결의 요금을 계산한다. 부분 **체결**은 지원하지만 별개의 부분 **청산 주문**·반복 재진입·다종목 포트폴리오는 지원하지 않는다. 기존 종목별 거래 정책을 변경하는 제한이 아니라 이 실험실의 지원 범위다.

[전용 저장소](../src/server/cost-execution-store.ts)는 새로운 메모리/시험 SQLite DB만 사용한다. 사용자용 화면·웹 API·실행 CLI는 추가하지 않았다. 개발 검사는 프로젝트 루트의 Windows PowerShell에서 기존 의존성을 사용해 실행한다. 검증 환경은 Node 24.20.0 / npm 11.19.0이다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/cost-execution.test.js dist/runtime/tests/cost-execution-store.test.js
```

정상 종료는 `pass 45`, `fail 0`, `cancelled 0`, `skipped 0`이다. 저장소 시험은 새 임시 폴더/DB와 직접 만든 자식 프로세스를 사용한다. 강제종료 도우미는 해당 시험에서만 실행하며 사용자 서버/DB를 대상으로 실행하지 않는다. 새 설치 검증은 아니며, 전체 제품 테스트나 실제 시장 백테스트와 구별한다.

사용 입력은 [합성 도우미](../tests/cost-execution-helpers.ts), 경계 사례는 [체결 검사](../tests/cost-execution.test.ts)와 [저장/복구 검사](../tests/cost-execution-store.test.ts)에 있다. 별도 API 키는 필요 없다.

## 계약과 상태

`SYNTHETIC_COST_EXECUTION_V1`은 `TEST_ONLY`, `SYNTHETIC_FIXTURE`, `liveEnabled=false`, 현재 원본 정책 해시만 받는다. 정수 수량·양수 가격·개별 체결 ID·발생/가용 시각이 필요하다. 한 기록의 비용 프로필은 고정되며 시작 시 알 수 있었고 유효해야 한다. 이후 프로필 만료·시각 역행·순번 누락·ID 내용 충돌은 HOLD한다. 최대 500사건·20주문·주문당 1,000주는 계산 자원 상한이지 투자 한도가 아니다.

| 사건/상태 | 처리 |
| --- | --- |
| ORDER | 현금/보유 잔량·예약 비용·단일 진입/청산 체인 검사 후 합성 기록 |
| FILL | 지정가·수량·발생/가용 시각·체결 ID 확인, 누계 비용의 증가분만 청구 |
| UNKNOWN / CANCEL_UNKNOWN | 잔여 현금·매도 수량 예약 유지, 새 주문 보류; 시간만으로 취소하지 않음 |
| CANCEL_REQUEST | 확정 전 예약을 해제하지 않음 |
| CANCEL_CONFIRMED | 최신 사건 이상인 근거 시각과 기체결 수량/대금이 일치해야 잔여 예약 해제 |
| 대체 SELL | 확정 취소된 직전 잔량에 연결, 새 주문의 과금 단위로 비용 재계산, 원본 최대 대체 2회 유지 |
| 중복 | 동일 사건은 재적용하지 않음; 동일 개별 체결의 재수신도 재청구하지 않음 |
| 모순/오류 | HOLD/예외로 거절, 저장소의 이전 확정 기록 보존; 자동 수정·재주문 없음 |

첫 SELL 이후 `replaces=null`로 횟수를 초기화할 수 없다. 처음과 대체 SELL 모두 현재 보유 잔량 전체를 대상으로 해야 하며, 초과 매도도 거절한다. 완료된 주문의 새로운 체결 통지, 누계만 있고 개별 체결이 없는 자료, 체결 취소/정정·환불은 지원하지 않는다. 실제 브로커 대조기의 확정 근거 수집·정확성은 이 함수가 입증하지 않는다.

ORDER/FILL 비용만 지원한다. DAY 누계·FX 그룹이 포함되면 보류한다. KRW/USD는 별도 실행의 원통화로 계산하며 환전을 자동 생성하지 않는다. 현금 결제는 명시한 `SYNTHETIC_IMMEDIATE`이며 실제 결제일·출금 가능액 모형이 아니다.

## 실제 요금과 예약금의 구별

ORDER 비용은 그 주문의 누적 체결 수량/대금, FILL 비용은 입력된 실제 개별 체결 단위로 계산한다. 예를 들어 주문 최소액 10에서 1주씩 2회 체결되면 차액 `10, 0`, 체결별 최소액 10이면 `10, 10`이다. 여러 주가 한 체결이면 FILL 최소액도 한 번만 부과한다. 미체결 취소에는 비용이 없고 대체 주문에는 새 ORDER 최소액이 적용될 수 있다.

매수 예약은 `잔량 × 지정가 + 남은 ORDER 비용 + FILL 비용 상계`다. ORDER는 잔량 전부가 지정가에서 체결될 때의 누계 비용에서 기청구액을 뺀다. FILL은 각 규칙의 최대 구간 요율을 사용한다.

```text
주당 변수 상계 = 지정가 × 최대bps / 10000    (NOTIONAL)
              또는 최대 주당 요율           (SHARES)
FILL 비용 상계 = 잔량 × Σ ceil(max(최소액, 고정액 + 주당 변수 상계) / quantum) × quantum
```

비음수 요율·정수 체결·매수 지정가 이하 가격에서 체결을 어떻게 분할하더라도 덮는 보수적 예약이다. “1주씩 나누면 항상 비용이 가장 크다”는 가정은 하지 않는다. 예약 상계를 실제 요금으로 차감하지 않고, 체결 이후 남은 예약을 재계산한다.

매도는 가격 상한이 없고 체결대금보다 요금이 클 수도 있다. 전체 체결만이 아니라 모든 부분체결 시점의 현금 부족을 예약한다. 규칙별 `K=max(최소액, 고정액)+quantum`, 최대 구간 요율을 사용하여 다음 선형 상계를 만든다.

```text
α = 모든 SELL NOTIONAL 최대bps 합 / 10000
A = Σ ORDER (K + 기체결 기준량의 최대요율 비용 − 해당 규칙 기청구액)
B = 모든 SELL SHARES 최대요율 합 + 모든 SELL FILL 규칙 K 합
부족 상계(k) = A + k × (B + (α−1) × 매도 지정가)
현금 예약 = max(0, 부족 상계(1), 부족 상계(남은 수량))
```

정수 체결의 건수는 체결 주수 이하고 `quantum`이 반올림 오차를 덮는다. `α≤1`이면 지정가보다 높은 매도가격이 이 부족 상계를 악화시키지 않는다. `α>1`은 이 최대요율 선형 상계로 가격 무상한을 처리할 수 없어 `SELL_COST_BOUND_UNSUPPORTED`로 보류한다. 일부 유한 구간만 높은 다른 계약까지 수학적으로 불가능하다는 주장은 아니다. 보수적 예약이 정확한 최소 필요 현금보다 클 수 있다.

## 저장·재시작과 보고

SQLite `BEGIN IMMEDIATE` 안에서 최신 기록을 읽고 전체 재생 검증 후 사건 저널·결과 해시·체크섬을 함께 저장한다. SQL 갱신 후 오류는 ROLLBACK한다. 재개 시 설정/정책/비용 해시와 재생 결과를 대조하므로 비용·예약을 중복 적용하지 않는다. 두 로컬 연결도 이전 메모리 상태로 덮어쓰지 않는다.

기존 파일은 명시 `resume`과 읽기 전용 사전검사를 통과해야 한다. 다른 형식의 DB/일반 파일은 채택하지 않는다. 새 파일은 배타적으로 만들며 초기화 실패 파일을 자동 삭제/초기화하지 않는다. 체크섬은 손상·불일치 탐지이며 관리자 변조 방어·실브로커 리더 권한 제어가 아니다. 네트워크 공유 DB와 악의적 파일 교체 경쟁은 지원/검증 범위 밖이다.

보고와 `learningEvidence`는 동일한 `costBasisHash`, 거래비용, 거래 순손익을 사용한다. 거래 순손익은 체결이 있고 보유 0·모든 주문 종료일 때만 제시한다. 운영비 미확정은 0원으로 바꾸지 않는다.

```text
거래 순손익 = 총 매도대금 − 총 매수대금 − 실제 거래비용
operatingCosts = UNRESOLVED
learningEvidence.status = HOLD
orderSubmissionAllowed = learningAllowed = liveEnabled = false
```

이 자료는 추후 연결을 위한 **학습 보류 근거**이며 기존 학습 입력/모델·전체 비용 차감 수익률이 아니다. `OPERATING_COST_ALLOCATION_UNSUPPORTED`와 `SYNTHETIC_COST_ENGINE_NOT_INTEGRATED`를 유지한다. 원래 수량 검사 결과를 여기서 주문 승인으로 받아들이지도 않는다.

## 공유 순수 비용 커널 — A 단계

[cost-kernel.ts](../src/core/cost-kernel.ts)의 `evaluateOrderCost(rawProfile, rawRequest)`는 한 주문의 개별 체결 명세에서 실제 누적 요금과 남은 현금 예약 상계를 계산한다. 기존 체결 실험실의 계산 부분을 추출했으며 현재 재사용 호출자는 위 합성 체결기다. 수량 계산기·공용 승인/체결 엔진·앱·학습·DB 스키마에는 연결하거나 변경하지 않았다.

입력/출력 계약은 `CostKernelRequest`와 `CostKernelResult` 타입으로 제공한다. 전달값은 타입 선언과 별개로 실행 시점에 엄격하게 검사한다.

| 입력 | 필수 의미 |
| --- | --- |
| contract/purpose/provenance | `SYNTHETIC_ORDER_COST_KERNEL_V1` / `TEST_ONLY` / `SYNTHETIC_FIXTURE` |
| policyHash/profileHash/scope/asOf | 현재 원본 정책, 전달 프로필과 시장/상품/통화, 계산 시점의 일치 |
| order | ID·BUY/SELL·정수 수량·지정가·접수 시각·호출자가 확정한 terminal 상태 |
| fills | 해당 주문의 중복 없는 전체 개별 체결: ID·orderId·수량·가격·발생/가용 시각. 누적 증분을 단일 체결로 추정하지 않음 |
| mode | 실제 요금만 `CHARGE_ONLY`, 요금과 잔여 예약 `WITH_RESERVATION` |

ORDER/FILL 과금만 지원하며 DAY/FX 규칙이 있으면 보류한다. 입력 금액은 기존 비용 계약의 최대 정수9자리·소수6자리, 주문당 최대1,000주·체결 명세1,000개다. 이는 계산 자원/정밀도 계약이지 투자 허용 범위가 아니다. ID 형식 제한을 완화하거나 입력을 잘라 맞추지 않는다. 주문 시점에 알려진 유효 프로필과 `order.at ≤ occurredAt ≤ availableAt ≤ asOf`를 검사하며, 빈 체결이나 terminal 입력도 바인딩·유효 기간을 건너뛰지 않는다.

성공 결과의 `charges.total`은 누적 실제 비용, `charges.orderTotal`은 그중 ORDER 과금, `charges.lines`는 항목별 근거다. 기존 체결기는 이전 확정 청구액과의 차액만 반영한다. `reservedCash`는 실제 청구가 아니라 향후 부족분의 상계이고, `CHARGE_ONLY`에서는 **null(미계산)**이다. 미계산을 예약금0으로 취급하면 안 된다. `WITH_RESERVATION`의 terminal/완전체결은 예약0을 반환한다.

같은 가격/금액이어도 프로필 버전·과금 단위·반올림·계산 모드·시각·개별 체결 근거가 다르면 `costBasisHash`가 다르다. 해시는 인증·주문 승인이나 완전한 자료를 받았다는 증명이 아니다. 입력은 수정하지 않으며 모든 결과의 주문/학습/LIVE 허용은 false다. 직접 호출의 중복 체결 배열은 HOLD하고, 기존 replay가 수행하던 수신 중복 제거는 그대로 유지한다.

커널은 terminal 상태의 진실 여부·취소 증거·UNKNOWN 해소·대체 계보·보유 수량·계좌 결제를 검증하지 않는다. 그 책임은 기존 체결기와 이후 공용 통합에 남는다. 가격 위험 R0·비용 포함 위험·운영비의 구별은 이전 설계를 유지하며 커널 자체가 수량/경제성을 승인하지 않는다. 기존 결과/보고/학습 보류 구조에 새 커널 해시를 끼워 넣지 않아 저장된 합성 자료의 해시 의미도 보존한다.

개발 검사는 프로젝트 루트 PowerShell에서 실행한다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/cost-kernel.test.js
```

[전용 시험](../tests/cost-kernel.test.ts)은38개로 KR/US·ORDER/FILL·같은 시각의 개별 체결·잘못된 입력·다른 비용 근거·빈 체결 유효성·BUY/SELL 전체 분할 및 각 부분체결 시점의 상계를 확인한다. 체결마다 가격이 달라지고 이미 일부 매도한 뒤에도 추가 현금이 필요한 사례를 포함한다. 실제 실행·독립 검토·관련 회귀 결과는 [PROGRESS · 공개 요약](PROJECT_STATUS.md)의 A 인수 기록을 따른다. 계좌나 키는 필요 없고 네트워크 요청·사용자 DB 변경도 없다.

## 검증과 남은 작업

새 45개 시험에서 누계/체결별 요금, 세 가지 반올림과 4주 전체 8분할, 매도 현금 부족·수량/체인·순번/시각·중복/상충, 재시작·원자 저장을 확인했다. 독립 읽기 검토에서 확인한 과소 예약·대체 링크 누락·매도 현금 미예약·부분 청산 잔량 고립을 수정 전 실패로 재현하고 보강했다. 상세 명령·실패/통과 로그·관련 회귀는 [PROGRESS · 공개 요약](PROJECT_STATUS.md)에 기록한다.

직접 만든 자식을 **COMMIT 후** 두 지점에서 강제 종료한 복구와 SQL 갱신 후 예외 롤백을 시험했다. 트랜잭션 도중 프로세스 강제 종료, 물리 전원 차단·디스크 고장 시험은 하지 않았다. 해시/시험 통과는 실제 계좌 안전성·수익성 보장이 아니다.

후속 [공용 엔진 비용 통합 설계](COST_ENGINE_INTEGRATION_PLAN.md)에서 소스 대조와 신규15개 시험으로 연결 경계를 확인했고 A의 공유 순수 커널을 추출했다. 독립 수량 계산기의 원본 가격 위험 R0 수정도 보존한다. 다음은 B의 새 합성 실행 사건·장부·원자 저장 계약 구현이다. 공용 승인/접수·체결·장부·학습 연결은 아직 없으며 기존 비례 비용·학습 스키마를 일부만 교체하지 않는다. 운영비 미결정이 걸리는 연결은 보류하고 별도 버전의 무운영비 합성 경로와도 의미를 구분해야 한다. D03-03/04 체크는 이 통합·검증 이후에만 완료할 수 있다. 실제 요율/API·모의계좌·실주문·OS 격리·웹 E2E·새 설치는 수행하지 않았다.
