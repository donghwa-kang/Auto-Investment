# B/P 신호와 비용 코어의 최소 합성 연결

_DEV-D03-S1/S2 · 2026-09-28 · 개발자용, 새 TEST_ONLY KRW 실행 한 건_

## 📋 구현 범위

[CostSignalProgram](../src/server/cost-signal-bridge.ts)은 기존 `PortfolioProgram`의 상품·자료 사전검사와 B/P 차트 평가를 재실행한 뒤, 선택한 **한 종목·한 프레임**의 근거를 기존 `CostReservationStore` V3 승인 입력에 연결한다. 새로운 현금 계산기나 두 번째 장부를 만들지 않는다. 기존 웹 앱·사용자 DB에는 활성화하지 않았다.

| 근거/역할 | 연결 대상 | 보존 조건 |
| --- | --- | --- |
| B/P 평가·손절·선택 호가 | 비용 포함 수량 승인 | 원래 정책과 평가 함수 재사용 |
| 비용 프로필·예약·체결 ID | 기존 V3 단일 저장소 | 기존 writer/epoch/COMMIT·멱등 검사 |
| 체결별 비용 posting | 기존 보고·학습 HOLD | 동일 `financialBasisHash` |

진입 후보가 생기는 정상 경로와, 비용·자료가 부적합해서 거절하는 경로를 모두 시험한다. `orderSubmissionAllowed`, `learningAllowed`, `liveEnabled`는 계속 false다. 여기서 CONFIRMED는 명시 합성 사건이지 브로커 응답이 아니다.

이 기능은 매수·매도 가격 경로를 스스로 생성하는 새 자동매매 앱이 아니다. S1 기본 모드는 테스트가 명시한 체결·매도·결제 사건을 사용한다. S2의 명시적 선택 모드에서는 공급한 합성 호가에 따라 기존 정책의 자동 청산을 실행한다. 기존 웹 앱·UI·전체 시장 반복 실행을 이 비용 경로로 교체하지 않았다.

## 🔧 실행과 성공 확인

기존 설치가 준비된 프로젝트 루트의 PowerShell에서 실행한다. Node 24.20.0과 기존 의존성을 사용하며 API 키·계좌·외부 연결이 필요 없다.

```powershell
npm run build:engine
node --test dist/runtime/tests/cost-signal-bridge.test.js
```

시험은 별도 메모리 DB 및 새 임시 폴더의 SQLite만 사용한다. 정상 시험에서 다음을 확인한다.

- B와 P의 실제 합성 차트 신호로 0보다 큰 정수 수량 승인
- ORDER/FILL 각각의 최소 과금, 1주씩 부분 체결, 매수 결제, 매도, 매도 결제
- 독립 BigInt 계산의 비용·손익·현금과 장부/보고/학습 HOLD 자료 일치
- 준비 요청의 JSON 보존 → DB 닫기/재열기 → 동일 요청/체결 재전송 시 중복 차감 없음
- 오래된 자료·변조된 승인·다른 Store·부적합 비용·기업행동의 거절

DB 닫기/재열기 시험은 정상 프로세스 안에서 수행한다. 실제 전원 차단·OOM·프로세스 강제 종료·HTTP 응답 유실을 새 연결 경로에서 검증했다고 해석하지 않는다. 시험용 준비 요청 파일은 제품 아웃박스 구현이 아니다.

## ⚙️ 입력과 호출 계약

`new CostSignalProgram(replayInput, portfolioSettings, selection)`은 원본 신호 재생 입력과 기존 포트폴리오 설정을 받는다. 외부에서 평가 성공 여부·진입 가격·손절값을 덮어쓰는 필드는 없다. `selection`은 다음 필드만 허용한다.

| 필드 | 의미 |
| --- | --- |
| `kind` / `purpose` | `SYNTHETIC_COST_SIGNAL_SELECTION_V1` / `TEST_ONLY` |
| `frameAsOf` / `catalogKey` | 재생 입력 안의 명시 프레임 시각과 KR 종목 키 |
| `profile` | 기존 합성 비용 프로필; 선택 상품·KRW·유효기간 일치 |
| `forecast` | 명시 `SYNTHETIC_POINT_SCENARIO`; 통계 추정/AI 예측 아님 |
| `adverseExitTicks` | 기존 비용 승인 입력의 명시 합성 마찰 |

전체 입력 예시는 [연결 시험의 fixture](../tests/cost-signal-bridge.test.ts)에 있다. fixture의 기대 매도가·q05는 실제 전망이 아니며 통과를 위한 실전 파라미터로 복사하지 않는다. 원래 후보 순서도 시험 순서이며 투자 우선순위가 아니다.

개발자 호출의 핵심은 아래와 같다. 입력 변수는 위 계약에 맞게 준비되어 있어야 한다.

```typescript
const program = new CostSignalProgram(replayInput, settings, selection);
const repo = new Repository(":memory:"); // 기존 사용자 DB 경로 사용 금지
repo.acquire();
try {
  const store = new CostReservationStore(repo, program.config(), {
    initialize: true,
  });
  const prepared = program.prepareEntry(store); // 읽기 전용 수량 검사
  store.reserve("entry-reserve", prepared); // 기존 단일 원자 저장
  store.handoff(
    "entry-handoff",
    store.prepareHandoff(program.reservationId, "CONFIRMED"),
  );
  // 이후 명시 합성 FILL/SELL/SETTLE는 기존 store.execute 경로만 사용한다.
  const evidence = program.evidence(store); // 보고/학습 HOLD, 상태 변경 없음
} finally {
  repo.close();
}
```

금융 상태의 파일 수명·저장·락·재전송은 기존 Store/Repository 계약을 따른다. 새 브리지는 DB를 열거나 옛 DB를 이관하지 않는다. 파일 실행은 **새 시험 디렉터리**에서만 만들고, 재개 시 동일 원본 입력·설정·선택으로 재구성해야 한다. 원래 `prepared`와 command ID를 보존해 재전송하며 새 상태에서 다시 만든 요청을 같은 command ID로 보내지 않는다.

## 🔍 정밀도·근거·보류 경계

ATR에는 기존 엔진이 계산한 40유효자리 이내 고정소수 문자열을 그대로 전달한다. 기존 `costSizingRequestSchema.atr`만 분석 지표 형식으로 확장했다. 숫자 타입·지수·NaN·Infinity·0·음수·40유효자리 초과는 거절한다. 금액/수수료/손절 입력의 기존 소수 6자리 제한은 바꾸지 않았다. 주식 수량만 범위를 확인한 정수 number를 쓰고 금액/ATR을 number로 변환하지 않는다. 손절의 호가 단위 정렬은 기존 `roundedEntry` 정책 그대로다.

`signalBasisHash`는 원본 재생 입력 해시, 설정이 포함된 프로그램 해시, 프레임, 상품, 평가/trace, 호가/거래량 기록, 명시 예측·비용 프로필을 묶는다. 새 원장의 config/manifest에 이 해시를 고정한다. `evidence()`는 기존 Store의 재생 검증된 내보내기에서 승인 입력이 신호 근거와 일치하는지 확인한 뒤, 기존 금융 보고를 그대로 묶는다.

새 증거 묶음은 로컬 내부 보고이며, 임의 외부 JSON을 인증하는 새 가져오기 API가 아니다. 금융 부분은 기존 `verifyCostOutcomeExport`에 별도로 보존한 config/exportHash를 주어 검증한다. 자체 기재된 해시만으로 외부 자료의 진위를 인정하지 않는다.

| 거절 사례 | 대표 사유 | 대응 |
| --- | --- | --- |
| KRW 대상/프레임 불일치 | `SINGLE_KRW_TARGET_REQUIRED` | 원본 대상 확인 |
| 차트 보류/복수 전략 | `SINGLE_VALIDATED_CHART_SIGNAL_REQUIRED` | 승인 강제 금지 |
| 상품/비용 범위 불일치 | `COST_PRODUCT_SCOPE_MISMATCH` | 올바른 명시 프로필 준비 |
| 최대 보유 창보다 짧은 비용 유효기간 | `COST_PROFILE_HORIZON` | 예약 전 차단; 유효기간 추정 금지 |
| 당일 예정 기업행동 | `PORTFOLIO_ACTION_WINDOW_UNSUPPORTED` | 원래 보류 유지 |
| 다른 실행/수정된 승인 | `STORE_BINDING_MISMATCH` / `SIGNAL_APPROVAL_MISMATCH` | 잘못된 연결 중단 |
| 비용/수량/시각 부적합 | `LOCAL_ADMISSION_HOLD` | 기존 위험 한도 완화 금지 |

생성/준비 단계의 HOLD는 오류 코드로 거절하며 금융 상태를 새로 쓰지 않는다. UI의 상태 표시나 영속 거절 목록을 추가한 것은 아니다. 직접 Store API를 호출해 다른 승인을 썼더라도 새 증거 묶음은 불일치를 거절한다. 이 내부 브리지는 적대적 코드에 대한 OS 접근 제어 경계가 아니다.

## 🔄 S2: 자동 체결·청산 틱 연결

새 실행에만 다음 네 번째 인자를 지정한다. 기존 S1/V3 DB에 옵션을 덧붙여 이관하지 않는다.

```typescript
const program = new CostSignalProgram(replayInput, settings, selection, {
  executionLoop: true,
});
// 위 예시와 같이 새 Repository/Store를 만들고 reserve → handoff한 뒤 호출.
store.tick("quote-delivery-1", {
  kind: "COST_LOOP_TICK",
  purpose: "TEST_ONLY",
  instrument: selectedInstrumentId,
  at: tickTimeMs,
  quote: {
    at: tickTimeMs,
    bid: "21399",
    ask: "21400",
    bidSize: 1000,
    askSize: 1000,
    halted: false,
  },
});
```

`selectedInstrumentId`는 승인 종목의 식별자, `tickTimeMs`는 이전 틱보다 큰 밀리초 시각이다. 가격은 고정소수 문자열, 시각/수량은 범위를 검사한 정수다. 위 가격은 시험 예시이지 매매 추천이 아니다. 완전한 실행 예시는 [cost-loop.test.ts](../tests/cost-loop.test.ts)를 따른다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/cost-loop.test.js
```

| 처리 | 계약 |
| --- | --- |
| 매수/매도 체결 | 나중 시각의 신선한 합성 호가, 기존 지연 1초·한 번에 최대 1주·지정가/잔량 대조 |
| 손절/익절 | 승인 손절 불변, 부분 체결 누적 VWAP 기준 기존 2R 목표 재계산; 감지 후 다음 틱 청산 요청 |
| 시간/리스크 청산 | 최초 매수 체결부터 90분, 세션 종료 10분 전/알려진 행사 한도 중 빠른 시점; AI 응답 없음 |
| 취소 | 기존 진입 TTL, 명시 합성 취소 지연 2초; 지연 중 부분 체결 허용, 이후 실제 누적 수량/금액 대조 |
| 미확정 | UNKNOWN/CANCEL_UNKNOWN은 시간만으로 확정하지 않음; 예약/노출 보존, 별도 명시 사건 필요 |
| 청산 대체 | 매수 잔량 취소 확정 후만 매도; 무진행 시 기존 최대 2회 대체·기준 호가 대비 가격 하한; 시장가 대체 없음 |
| 결제 | 이전 틱까지의 확정 체결을 다음 틱의 명시 TEST_ONLY SETTLE로 정산; 현실의 결제일 예측 아님 |
| 초과 손실 | 정상 형식·지정가 범위의 확정 체결은 기록한 뒤 예산 초과 HOLD; 청산/취소를 지워 숫자를 맞추지 않음 |

한 틱은 한 `commandId`/DB revision을 갖는다. 그 안에서 생성된 개별 ORDER/FILL/CANCEL/SETTLE은 각기 다른 사건 ID를 갖고 기존 장부에 누적된다. 동일 command ID와 동일 내용의 재전송만 원래 영수증을 반환한다. 다음 틱에 같은 command ID를 쓰면 충돌이다. 틱 전체 원문·체결 ID 인덱스·비용·예약·상태 캐시·감사 기록은 기존 writer/epoch 아래 한 COMMIT이다. 중간 부분 매도 수량을 완성된 관측으로 평가하지 않고, 최종 수량/관측을 반영한 뒤 마감 카운터와 위험 상태를 확정한다.

Append-only는 명령/금융 사건 이력에 적용한다. 기존 SQLite 상태 캐시의 트랜잭션 내 UPDATE/UPSERT까지 금지한 것이 아니다. 기존 이력 재생 대조와 해시 검증을 생략하지 않는다. 신규 진입 HOLD와 이미 확인된 체결 사실, 잔여 위험 축소를 구분한다. 사람의 승인이나 AI 출력으로 멱등/금액 검증을 우회하지 않는다.

`store.read().loop`에서 `status`, `reason`, `target`, `deadline`, `holds`, `exitBlocked`를 확인한다. `HOLD`는 청산 성공을 뜻하지 않는다. 가격/대체 한도 차단은 다음 호가만으로 해제되지 않으며, 기존 제출 주문의 유효 체결은 계속 기록할 수 있다. 잘못된 구조/다른 종목/미래 호가/역행 시각은 쓰기 없이 거절한다. 오래된 호가나 거래정지는 체결을 만들지 않고 HOLD를 기록한다. 실제 매매 상태는 원장 주문·잔여 수량·결제와 함께 판단해야 한다.

### 안전·성능 범위

AI/네트워크 호출은 없지만 **전체 루프가 O(1)이거나 실시간 지연 목표를 달성했다는 뜻은 아니다**. 기존 Store의 전체 이력 재생·원자 커밋 비용이 있고, 이 단계는 드문 합성 틱을 주입하는 로컬 검증기다. 가격 판단과 금융 기록 책임은 분리하되 검증 생략이나 별도 금융 쓰기로 속도를 높이지 않는다. 실서비스의 수신 큐·스케줄러·백프레셔·지연 계측은 후속 범위다.

이 모듈은 자체 타이머나 백그라운드 수신기를 시작하지 않는다. **틱 호출이 없으면 시간 청산 판단도 실행되지 않는다.** 90분 시험은 합성 시각을 전진시켜 경계에서 청산 의도가 생기는지 검사한 것이며, 실제 90분 상주 실행·단절 중 청산 보장은 아니다. 불리한 호가/미확정 주문 때문에 청산이 지연될 때는 보유 사실을 남기며 강제 성공 처리하지 않는다.

명시 S2 실행은 틱 최대 4,096회, V3 명령 최대 5,200회, 개별 장부 사건 최대 500개와 기존 청산용 여유 공간 검사를 따른다. 내부 관측은 한 틱 명령에 속하며 기존 외부 제어 명령 100회 한도를 소모하지 않는다. 기존 S1/V2/V3 계약의 한도는 그대로다. 한도 도달/관측 기간 소진은 거래 종료 증거가 아니며, 남은 노출을 보존하고 시험을 중단한다. 지속 운용용 저장소 용량을 검증한 것이 아니다.

루프 실행의 장부 관측 기간은 비용 프로필 만료 직전과 세션 종료 중 빠른 시점까지로 확장한다. 이는 첫 부분 체결부터 90분 후 청산 요청과 그 취소/체결을 기록할 여유이지 보유 한도를 늘리는 정책 변경이 아니다. 관측 구간 안에 청산이 완료된다고 보장하지 않는다. 늦은/휴장/갭 상황에서 실제 청산 가능성은 미검증이다.

시험은 정상 프로세스의 DB 닫기/재열기 및 쓰기 단계/커밋 실패 주입이다. 실제 전원 차단·OOM·HTTP·OS 격리, 실제 브로커의 취소/부분 체결, 연속 장중 처리 성능을 증명하지 않는다. 호출자가 원래 틱 ID/입력을 보존해야 하며 이 단계에서 제품 클라이언트 아웃박스를 새로 만들지 않았다. 보고/학습/실주문 권한은 계속 false다.

### 실행 방법과 독립 기대값

기존 설치가 준비된 프로젝트 루트 PowerShell에서 실행한다. 첫 명령은 TypeScript 원본을 빌드하므로 `dist/runtime/tests/cost-loop.test.js`를 직접 편집하지 않는다.

```powershell
npm run build:engine
# 새 극단 경로만 실행
node --test --test-concurrency=1 --test-name-pattern=CL-X dist/runtime/tests/cost-loop.test.js
# 기존 S2와 새 극단 경로를 함께 실행
node --test --test-concurrency=1 dist/runtime/tests/cost-loop.test.js
```

새 임시 SQLite만 생성한다. 시험은 비용이 큰 전체 이력 재생을 포함하므로 즉시 끝나는 속도 측정용 프로그램이 아니다. 기대값은 다음의 한정된 조건으로 독립 검산한다.

- 초기 현금 5,000,000원, 승인4주, 진입21,400원, 손절21,121원인 기존 B 신호 fixture
- 과금 단위 ORDER, 1bp/최소10원, 해당 주문금액에서는 최소 과금이 적용되는 고정 프로필
- 원 단위 정수 BigInt로 매수/매도 대금·확정 비용·미수/미지급·현금·예약·가용현금 계산
- 각 체크포인트의 예정된 체결/결제 개수로 계산하며 운영 코드의 비용 함수나 실제 출력 체결 목록을 기대값 생성에 사용하지 않음
- 주문 ID/상태/수량/지정가, HOLD 사유, 보유 한도, 청산 손익/손실 카운터와 같은 원장 근거의 보고 재생 대조

`Available = C - P - Q`에서 C는 현금, P는 미지급, Q는 예약금이다. 미수 R은 아직 가용현금에 더하지 않는다. `C + R - P`는 여기서 **현금성 순자산**이며, 보유 주식이 남아 있을 때 계좌 전체 자산이라고 부르지 않는다. 미체결 노출이 남는 사례는 손익0/청산 성공으로 포장하지 않는다.

원래 요청 ID로 재시도하는 경우와 동일 체결 ID를 다른 전달 ID로 재전송하는 경우를 분리한다. DB 재열기/재전송/상충 거절/보고 내보내기 전후 상태 해시를 대조한다. 기존 검증기로 전체 명령을 재생해 각 영수증과 최종 보고가 일치하는지 확인하며 모든 실행·학습 권한은 false다.

### 발견 결함과 보유 시간 기준

CL-X05에서 실제 체결1.5초가 먼저 발생했지만 4초에 도착하고, 기존 수신 기록에는 2초/3초 체결이 먼저 들어오는 상황을 사용한다. 기존 루프는 첫 수신 체결의 기록 시각2초를 기준으로 계산해 보유 종료를 0.5초 늦췄다. 수정 후 `min(confirmed occurredAt)`으로 최초 실제 체결 시각을 찾고, 기존 deadline과 새 계산 중 더 이른 값을 적용한다. 원본90분 규칙·금액·체결 수신 이력/해시는 임의로 고치지 않는다.

이미 저장된 S2 합성 실행이 이 결함 조건을 포함하면 과거 캐시/영수증과 수정된 재생 결과가 달라 검증이 거절될 수 있다. 자동 이관/해시 덮어쓰기를 제공하지 않는다. 원래 DB·입력·오류를 보존하고 새 시험 DB에서 재현해야 한다. `occurredAt === at`인 일반 합성 체결의 기존 의미는 유지한다.

### 해석할 때의 한계

시험 통과는 이 고정 경로의 상태/회계 정합성 증거이지 수익성·모든 시장 예외·실제 브로커 속도의 증거가 아니다. KRW 단일 종목·최우선 호가·정수 주식·고정 합성 비용 범위다. USD/다종목, 호가 깊이/큐 우선순위, 비용 변경, 거래소 재개 경매·체결 정정은 검증하지 않는다.

CL-X04의 입력 없음 단계는 코어를 호출하지 않았을 때 상태가 유지되는 **현재 한계 확인**이다. 타이머가 동작한다는 검증이 아니며, 시간 경계 입력도 시험에서 명시적으로 넣는다. 재시작은 정상 DB 닫기/재열기이며 전원 차단·OOM·HTTP 응답 유실이나 제품 아웃박스 시험은 아니다. 후속 작업은 별도 승인 범위에서 상주 타이머/입력 단절 대응을 구현하고, 그다음 앱 연결을 검토한다.

## 🔍 S4: 로컬 시간 감시와 입력 단절

[시간 점검 코어](../src/core/cost-watchdog.ts)와 [실행기](../src/server/cost-loop-runtime.ts)는 **새 TEST_ONLY 단일 KRW 실행에만** 선택적으로 적용한다. 기존 S2/S3 실행과 웹 앱은 그대로이며 실시간 브로커 연결이 아니다. 위 S2/S3의 타이머 부재 설명은 해당 기존 계약에 대한 기록이다. S4는 원래 정책/프로필·금융 계산을 바꾸지 않고 타이머를 통한 위험 감지만 추가한다.

### 입력 종류와 권한

| 입력/동작 | 허용되는 효과 | 만들지 않는 증거 |
| --- | --- | --- |
| `store.pulse(id, command)` | 시간 한도/호가 단절/주문 검토 필요, 영속 HOLD·감사 | 주문·체결·결제·취소 완료·새 시세 |
| `runtime.quote(id, tick)` | 선행 시간 점검 후 기존 S2 합성 틱 처리 | 실제 브로커의 체결·결제 증거 |
| `runtime.start()` | 즉시 검증 후 한 개의 Node 타이머 예약 | lease 자동 재취득·HOLD 해제 |
| `runtime.stop()` | 타이머 취소·이전 콜백 무효화 | 청산 완료·주문 취소·예약금 반환 |
| `runtime.status()` / `failure` | 메모리의 실행 상태·지연·오류 확인 | 저장 실패 시 영속 HOLD가 생겼다는 보증 |

타이머는 `COST_LOOP_PULSE`라는 별도 명령이다. 호가를 복제하거나 시각을 바꿔 `tick()`으로 전달하지 않는다. 금융 사건 목록, 수량·현금·비용·예약·미수/미지급·마감/손실 카운터·마지막 금융 관측 시각을 변경하지 않는다. 변경된 감시 상태·입장 보류·명령 영수증·감사는 기존 Store의 동일 writer/epoch/COMMIT 안에 저장한다. 점검 시각은 명령 `at` 및 `loop.watchdog.lastPulseAt`이며, 금융 보고의 `asOf`가 최신 시세 시각으로 갱신됐다는 뜻이 아니다.

### 점검 규칙과 보수적 보류

- 유효 호가 부재: 마지막 사용 가능한 호가가 기존 최대2초보다 오래되면 `WATCHDOG_INPUT_STALE`; 처음에는 승인에 사용한 호가 시각이 기준이다. 거래정지 호가로 신선도를 연장하지 않는다.
- 진입 대기: 기존10초 TTL에 도달한 미종료 BUY는 `WATCHDOG_ENTRY_CANCEL_REQUIRED`. 타이머가 취소 접수/완료나 예약 반환을 대신하지 않는다.
- 청산 대기: 미종료 SELL의 기존2초 무진행 기준에 도달하면 `WATCHDOG_EXIT_REVIEW_REQUIRED`. `UNKNOWN`/`CANCEL_UNKNOWN`에는 `ORDER_RECONCILIATION_REQUIRED`도 남긴다.
- 보유 시간: 확정 체결의 가장 이른 `occurredAt`과 기존 세션/행사 한도에서 마감을 계산한다. 이미 알려진 한도를 늦추지 않으며 도달 시 `WATCHDOG_TIME_EXIT_REQUIRED`와 청산 의도를 기록한다. 늦게 발견했으면 발견 시각을 기록하고 과거에 처리했다고 소급하지 않는다.
- 관측 기간 종료: 노출/미결제가 남으면 `WATCHDOG_HORIZON_EXHAUSTED`를 남긴다. 실행기는 기간 도달 시 `FAULT`로 중단하며 자동 연장·성공 마감을 하지 않는다.

감시 경고가 생기면 `WATCHDOG_REVIEW_REQUIRED`로 신규 승인을 보류한다. 새 호가·잔여 수량0·재시작만으로 경고/권한을 해제하지 않으며, 이번 단계에는 해제 API가 없다. 이미 확인된 금융 사실과 허용되는 위험 축소는 기존 장부 규칙에 따라 처리할 수 있다. 경고가 있는 상태에서 합성 매도가 끝나도 실행 허가가 자동 복원되지 않는다.

새 opt-in 실행은 직접 `store.tick()`을 호출해도 필요한 시간 점검을 건너뛸 수 없다(`COST_WATCHDOG_CHECK_REQUIRED`). 확정 체결의 실제 발생 시각은 과거여도 되지만 **새 전달 사건의 기록 시각**을 마지막 감시 사건보다 과거로 만들 수 없다. 동일 명령·동일 내용 재전송은 원래 영수증으로 처리하며 내용 변경은 충돌이다.

### 개발자 사용 계약

기존 S1 예제의 새 `CostSignalProgram` 생성 옵션에만 `{ executionLoop: true, watchdog: true }`를 지정한다. 기존 DB 설정을 덮어써 감시 기능을 켜지 않는다. 새 Repository의 lease 획득·Store 초기화·예약·합성 인계가 끝난 뒤 실행기를 만든다.

```typescript
import { CostLoopRuntime } from "./src/server/cost-loop-runtime.js";

// store: 위 옵션으로 새로 만든 합성 실행의 CostReservationStore
// fixtureClock: 이 실행의 합성 시각과 경과 시간을 제공하는 시험 시계
const runtime = new CostLoopRuntime(store, { clock: fixtureClock });
runtime.start();
try {
  // 테스트 공급자는 command.at을 현재 처리 시각으로 명시한다.
  // quote.at은 실제 합성 관측 시각 그대로이며 과거 호가를 새것으로 바꾸지 않는다.
  runtime.quote("quote-1", fixtureTick);
  console.log(runtime.status());
} finally {
  runtime.stop(); // 청산/취소/DB 닫기를 뜻하지 않는다.
}
```

위 코드는 기존 예제의 `store`·시험 시계·입력을 사용하는 API 발췌다. 독립 실행 스크립트는 아니며 아래 명령이 완전한 실행 검증 경로다. `start()`는 동기 시작이며 타이머가 실제 작동하려면 이벤트 루프를 돌려야 한다. 즉시 `stop()`하면 상주하지 않는다. 테스트는 실제 타이머 콜백을 기다린 후 멈춘다.

기본 시계는 `Date.now()`/`performance.now()`, 기본 타이머는 Node `setTimeout`이다. 과거 합성 실행에는 해당 합성 시각에 맞는 명시 시험 시계를 주입해야 한다. 현재 날짜를 과거 세션에 섞으면 기한 초과로 중단한다. `quote()`의 처리 시각이 현재 실행기 시각과 다르면 `COST_RUNTIME_QUOTE_PROCESSING_TIME`으로 정지한다. 임의 입력을 고쳐 받아들이는 실자료 어댑터가 아니다.

타이머 간격은 기본250ms, 허용100~1000ms이며 **처리 지연 보장이 아닌 로컬 점검 설정**이다. 이전 점검이 끝난 뒤 한 번만 예약하고 밀린 횟수만큼 콜백을 몰아 실행하지 않는다. 동기 Store 호출을 같은 JavaScript 실행 흐름으로 직렬화하고, 재진입은 거절한다. 같은 Store에 두 실행기를 시작하지 못하며 다른 객체의 `stop()`으로 실행 중 소유권을 해제할 수 없다. 여러 Store 래퍼/프로세스의 배타성은 기존 DB lease·revision 검증에 의존한다.

매번 금융 명령을 저장하지 않는다. 새로운 경고/한도 변화가 있을 때만 감시 명령을 저장하며 동일 상태는 `COST_WATCHDOG_NO_CHANGE`로 거절한다. 감시 명령은 실행당 최대64개, 원래 전체 명령/틱/금융 사건 상한은 보존한다. 이 상한은 정책 수익/위험 기준이 아닌 시험 자원 한도다. 반복 점검은 lease heartbeat와 읽기 검증을 하므로 디스크 I/O가0이라는 뜻은 아니다.

벽시계가 멈춰도 단조 경과 시간을 함께 사용해 점검한다. 시계 역행·유효하지 않은 시각·저장/lease 오류는 `FAULT`로 중단하고 타이머를 취소한다. 오류 원문은 `failure`에 유지한다. 이미 만료된 lease를 갱신하거나 소유권을 재획득하지 않는다. 새 실행기로 수동 재개할 때도 DB 재생·기존 절대 마감·영속 경고를 사용한다. 재시작을 새90분 시작으로 취급하지 않는다.

### 실행 검사와 범위

프로젝트 루트 PowerShell, 기존 Node24 설치에서 실행한다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/cost-watchdog.test.js
```

[감시 테스트](../tests/cost-watchdog.test.ts)는2초/10초/90분 경계, 단절 후 호가, 같은 시각의 타이머/호가 양쪽 순서, 중복/상충, 미확정 취소/매도, 늦은 최초 체결, 정상 DB 재열기, 시계 역행/정지, 오류/기한 종료, 쓰기5단계 및 커밋 실패를 검사한다. 고정 자본500만원·4주·가격21400원의 원 단위 BigInt 기대값과 기존 비용 보고/재생을 대조한다. 실제 Node 타이머의 무입력 감지와 시험 프로세스의350ms 이벤트 루프 지연도 별도로 검사한다. 실제 통과 수·실패 이력은 [진행 기록 · 공개 요약](PROJECT_STATUS.md)을 따른다.

이 기능은 **청산 필요 감지이지 청산 성공 보장**이 아니다. 같은 프로세스가 멈추거나 SQLite 재생/쓰기가 오래 걸리면 타이머도 지연된다. 외부 프로세스 감시, OS 전원/OOM·컴퓨터 절전,90분 실제 상주·장중 처리량/백프레셔, 실제 네트워크 입력/아웃박스·브로커 대조, 다종목/USD·UI·AI·실자료 수익성은 검증하지 않는다. 재시작 사이의 실제 시간 신뢰성은 호스트 시계에 의존한다. 데이터가 없을 때 손절/목표가 도달 여부를 추측하지 않는다. 다음 범위는 이 계약을 사용하는 앱 연결이며 기존 금융/정정 정책 완료를 대신하지 않는다.
