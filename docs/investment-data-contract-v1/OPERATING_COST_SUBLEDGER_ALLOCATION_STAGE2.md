# 운영비 보조장부·시험 보고 배분 — 2단계

새 합성 비용 장부를 재생·대조하고 완료된 모의 거래에 비용을 정확히 나누는 개발용 모듈 안내다. 기존 앱의 실제 비용 처리나 학습 자동 연결은 아직 제공하지 않는다.

---

## 🎯 범위와 기존 기능의 관계

[1단계](OPERATING_COST_ESTIMATION_STAGE1.md)는 후보 심사에 사용할 운영비를 추정한다. 이번 2단계는 별도 `TEST_ONLY` 원화 보조장부의 발생·지급·예약을 검증하고, 명시한 시험기간의 비용을 검증된 국내 모의 거래에 배분한다. 원본 정책·위험 수치·상품 허용 범위는 그대로다.

| 제공 모듈 | 동작 | 자동으로 연결하지 않는 곳 |
| --- | --- | --- |
| [operating-journal](../../src/core/operating-journal.ts) | 의무·지급·예약 ID별 재생, 합계와 잔액 대조 | 기존 계좌 장부·DB·월 지출 승인 |
| [operating-allocation](../../src/core/operating-allocation.ts) | 엔진 내보내기 검증 후 정수 배분·순손익 보고 | 거래 승인·위험 한도·연속손실 중지 |
| 같은 모듈의 가용시각 검사 | 원자료 재계산·보고 해시·이용 가능 시각 확인 | 실제 학습 정답·모델 교체 |

기존 웹 UI·서버·사용자 DB는 이 모듈을 호출하지 않는다. 별도 HTTP API·CLI importer·운영비 입력 화면도 없다. 실제 자료를 합성 표식으로 바꾸어 넣는 기능이 아니다. 보고서의 `actualLearningAllowed`와 `accountMutationAllowed`는 항상 `false`이고 기존 `OPERATING_COST_ALLOCATION_UNSUPPORTED` 보류도 유지한다.

## 🧮 비용 인식과 지급의 분리

`RECOGNIZE`는 의무 하나의 비용과 미지급 채무를 한 번 인식한다. `PAY`는 그 의무를 전액 지급하여 현금·채무만 줄인다. 비용을 다시 인식하지 않는다. 다음은 주식 평가액을 포함하지 않는 **비용 전용 보조장부** 예시다.

| 상태 | 현금 | 미지급 채무 | 누적 발생 비용 | 순자산 상당액 |
| --- | ---: | ---: | ---: | ---: |
| 초기 | 1,000원 | 0원 | 0원 | 1,000원 |
| 비용 50원 인식 | 1,000원 | 50원 | 50원 | 950원 |
| 같은 의무 50원 지급 | 950원 | 0원 | 50원 | 950원 |

`netEquityKrw = cashKrw - payableKrw`이며 전체 투자 계좌의 E가 아니다. 발생 채무가 초기 현금보다 크면 음수 상태도 보존한다. 자금 부족을 숨기거나 이미 발생한 비용을 삭제하지 않는다. 현금을 초과하는 지급은 거절한다.

`RESERVE`는 미발생 의무의 금액을 예약한다. `RECOGNIZE`에 연결한 예약 ID·의무 ID·금액이 모두 일치해야 해당 예약만 전환된다. A50원+B50원에서 A를 인식하면 B50원만 예약으로 남는다. `RELEASE`는 아직 발생하지 않은 예약의 해제이며 지급 취소·환불이 아니다.

같은 이벤트 ID·같은 내용의 재수신은 한 번만 반영한다. 같은 ID의 내용 충돌, 다른 ID로 같은 의무 재인식·재지급, 잘못된 예약 연결은 거절한다. 새 지출을 승인하는 기능은 없으며 `newSpendingApproved=false`다. 월 한도·동시 지출 승인·보호 서비스 연속성은 별도 통합 과제다.

## 🔌 입력 계약과 개발 사용법

계약은 `OPERATING_JOURNAL_TEST_V1`과 `OPERATING_ALLOCATION_TEST_V1`이다. 정확한 필드는 모듈의 strict 스키마, 실행 가능한 입력은 [장부 시험](../../tests/operating-journal.test.ts)의 `input()`과 [배분 시험](../../tests/operating-allocation.test.ts)의 `input()`을 참조한다.

| 입력 | 이번 계약 |
| --- | --- |
| 공통 표식 | `TEST_ONLY`, `SYNTHETIC_FIXTURE`, `liveEnabled=false` |
| 장부 시작 | 초기 현금만 지정. `startsEmpty=true`, 초기 채무·예약 없음 |
| 완전성 | 장부와 보고기간 모두 `complete=true` 필요. 선언 자체가 외부 자료의 완전성을 증명하지는 않음 |
| 금액 | 30자리 이하 비음수 원화 정수 문자열. 계산은 BigInt, 분할 지급·외화·음수 정정 미지원 |
| 사건 | 최대 10,000행. 중복 정규화 후 sequence 1부터 연속, 발생·가용시각 각각 비감소 |
| 연결 | 현재 원본 정책 해시 일치, 장부와 모의 내보내기의 실행·정책 해시 일치 |
| 보고기간 | 시작 포함·끝 제외. 시험자가 명시하며 자동 일/월 마감 기준이 아님 |
| 정정 | `corrections=NONE_DECLARED`. 환불·소급 정정 처리 정책을 결정한 것이 아님 |

기존 원본 정책은 대문자 바이트 해시, 새 내용 해시는 소문자 SHA-256 형식을 그대로 사용한다. 이전 정책이나 기록의 해시를 바꾸지 않는다.

`replayOperatingJournal(raw)`는 새 뷰를 반환하고 입력을 수정하지 않는다. `verifyOperatingJournalView(raw, claimed)`는 저장된 잔액·합계를 믿지 않고 재생 결과와 대조한다. `buildOperatingAllocation(raw)`는 기존 `verifyPaperExport`로 체결·수량·수수료·청산과 기록 간 일관성을 먼저 검증한다. 해시는 변경 탐지용이지 외부 출처 인증이나 완전성 보증이 아니다.

### 로컬 검사 재현

기존 [프로젝트 실행 환경](../../README.md)의 의존성이 설치된 프로젝트 루트에서 실행한다. 사용자 DB나 키 경로를 지정하지 않는다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/operating-journal.test.js dist/runtime/tests/operating-allocation.test.js
```

정상 조건은 빌드 종료 0, 시험의 실패·취소·건너뜀 0이다. 새 임시 합성 DB/파일만 사용한다. JSON 저장·재읽기 시험은 DB 트랜잭션 실패·앱 재시작·실제 OS 복구의 증거가 아니다. 실제 결과와 개발 중 실패는 [진행 기록 · 공개 요약](../PROJECT_STATUS.md)에 구분한다.

## 📊 정확한 배분과 시간 경계

O는 시험기간 안에 발생한 비용 합계다. N은 해당 기간 안에 진입·청산했고 관련 주문이 최종 상태인 고유 완료 거래 수다. 부분 체결은 거래 수를 늘리지 않으며 체결 없는 취소도 분모에 넣지 않는다. 기간을 가로지르거나 열린 거래는 조용히 제외하지 않고 보고를 보류한다. 기존 내보내기의 미분류 비용은 0원이어도 이 단계에서 합치지 않는다.

N>0이면 `O / N`의 정수 몫을 각 거래에 배분하고 나머지 1원씩을 ASCII 거래 ID 순서로 나눈다. O=10원/N=3이면 4·3·3원으로 합계 10원이다. 후보 추정 4원을 세 번 비용 인식하지 않는다. N=0이면 O 전체가 `unallocatedKrw`로 남고 비용을 삭제하지 않는다. 거래별 순손익 표시는 기존 거래 손익에서 배분액을 한 번 빼며 기존 장부 잔액을 변경하지 않는다.

자료 시각은 아래를 모두 만족해야 한다.

- 장부와 엔진 기록의 시작 시각은 보고기간 시작 이하.
- 보고기간 끝 ≤ 각각의 장부/내보내기 `asOf` ≤ `finalizedAt` ≤ `availableAt`.
- 각 비용은 해당 장부 `asOf`까지 알려져 있어야 하며, 역순으로 늦게 도착한 사건은 자동 정정하지 않음.
- 보고기간 종료 전 생성되어 아직 남은 예약은 기간 시작 전의 예약도 보류. 종료 정각 이후 신규 예약은 해당 기간 예약으로 간주하지 않음.

마감 뒤의 비용·지급·예약 해제가 포함된 최신 스냅샷으로 과거 마감을 재구성할 수 없다. 과거에 완성된 해당 시점 스냅샷을 사용해야 한다. 보고서 가용시각 뒤의 검사만 `AVAILABLE_TEST_ONLY`를 반환하고, 그 경우도 `actualLearningAllowed=false`다. `assessOperatingAllocationAvailability(raw, expectedReportHash, asOf)`는 호출 시마다 원자료부터 다시 대조한다.

## ⚠️ 미결정·검증 한계와 다음 단계

[운영비 명세](OPERATING_COST_SPEC.md)의 OC-U01–08은 해결된 것으로 표시하지 않는다.

| 미결정 | 이번 처리 |
| --- | --- |
| U01 초기 부분 이력, U04 D/증가분 | 기존 1단계 추정 규칙 유지, 이 보고 모듈에서 결정하지 않음 |
| U02 공유 구독 귀속, U03 외화 환산 | 명시 합성 KRW만 허용. 미국/혼합 시장 내보내기도 보류 |
| U05 환불·정정 | 이번 계약에서 미지원, 음수나 덮어쓰기로 대체하지 않음 |
| U06 자동 마감·연속손실 | 명시 시험기간 보고만 제공, 기존 즉시 판정/중지 래치 불변 |
| U07 늦은 비용·체결 | 미래 스냅샷·소급 입력 거절. 과거 보고 재작성 정책은 미결정 |
| U08 실제 장부 범위 | 별도 보조장부만 제공. 기존 DB·다일 장부·재시작·입출금 통합 미지원 |

배분 시험은 새 합성 엔진의 실제 2거래 기록을 사용한다. 4·3·3원 산술을 위한 세 번째 거래는 ID를 분리한 명시 합성 복제이며 세 거래의 엔진 실행 증거로 세지 않는다. 입력 검증과 시험 통과는 투자 수익성·실제 공급자 기록의 진위·악성 코드용 OS 격리 검증이 아니다.

다음은 자동 보고 마감, 비용 확정 전후 연속손실 판정, 늦은 정정, 장부 적용 범위의 계약을 확정하는 일이다. 그 뒤 새 버전 저장·복구·승인/접수·학습 경로를 연결해야 한다. 현재 앱에서 거래를 시작해도 이번 보조 모듈이 자동 적용되지 않는다. 계좌·키·API·유료 AI·실지급·실주문을 연결하지 않았다.
