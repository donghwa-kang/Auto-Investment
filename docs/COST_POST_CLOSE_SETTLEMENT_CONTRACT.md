# 마감 후 지급·결제 계약 — D9-A

2026-09-27 · DEV-D03 내부 설계 · **D9-A 계약 검토·검산 완료, 후속 D9-B 구현 결과는 별도 안내 참조**

이 문서는 [D8 원자 마감](COST_FINALIZATION.md)의 다음 개발 범위를 정의한다. 이미 비용과 손익에 반영된 채무·미수금의 지급·결제만 후속 사건으로 기록하고, 확정된 과거 결과는 바꾸지 않는다. 새 합성 KRW 실행의 선택 확장부터 구현한다. 실제 API·키·계좌·주문·유료 AI·앱 연결은 없다.

이 문서는 D9-A 당시의 사전 계약이다. 당시 마감 후 결제는 미구현이었고, 이후 [D9-B 구현 안내](COST_POST_CLOSE_SETTLEMENT.md)의 새 명시 합성 실행에만 후속 명령을 추가했다. 기존 PAY/SETTLE 경로는 여전히 마감 뒤 차단된다. 아래 계약 정의와 D9-A 당시 검산은 D9-B 실행 결과를 대신하지 않는다. 기존 1위험일 거래 계약을 다일 거래로 확대하지 않는다.

마감 이후의 현금 이동을 기록하기 위해 과거 원장을 다시 열거나 기간을 늘리지 않는다. 같은 DB의 명령 이력에 후속 결제 사건을 추가하고, 마감 당시 잔액에 그 사건의 차액만 적용해 현재 잔액을 재생한다.

## 🔐 활성화·기준점·불변식

### 새 실행에서만 선택

설명용 확장명은 `POST_CLOSE_SETTLEMENT_FIXTURE_V1`이다. 구현 때 독립 계약 해시와 엄격한 설정 스키마를 정의하고, 빈 새 실행을 초기화하기 **전** 명시 옵션으로 넣어 전체 configHash에 포함한다. 기존 V1~V4·D8 계약 해시를 바꾸거나 기존 DB에 옵션을 사후 주입하지 않는다. 구형 파일 자동 이관은 별도 미승인 범위다.

기존 D8 해시의 `RAW_QUARANTINE_NO_FINANCIAL_MUTATIONS`는 기본 계약의 기능 경계다. D9는 이 기본 계약을 소급 수정하는 것이 아니라 명시 확장으로 능력을 추가한다. 따라서 기능 판정·보고/내보내기의 호환 검사는 **기본 해시 + 확장 해시 + 전체 configHash**로 수행해야 한다. 기본 D8 해시 하나만 보고 D9 실행을 구형 계약으로 수용해서는 안 된다.

설정에는 합성 후속 관찰 종료 시각 `followupEndExclusive`가 필요하다. 이는 유한한 시험 구간이며 실제 거래소 결제 기한이나 신규 매매 허용 시간이 아니다. 기존 매매/비용 horizon, 가격·요율 유효 기간은 불변이다. 마감 시각이 이 구간에 들어오지 않으면 해당 확장의 마감을 보류한다.

### 마감 기준점과 현재 상태의 구분

D9 선택 실행의 최초 D8 마감 COMMIT에서 기존 체크포인트와 함께 후속 기준점을 저장한다. 내용은 마감 revision·원래 closeId·체크포인트 해시, 마감 시 공통 잔액, 미지급 의무/미결제 posting의 유한한 목록과 원본 해시다. 이 목록은 **동일 트랜잭션에서 검증한 마감 직전 prefix**에서 파생하고, 나중 현재 상태를 기준으로 다시 만들지 않는다. 자신을 포함한 stateHash로 자기 자신을 검증하는 순환 해시는 금지한다.

| 보존 영역 | 허용되는 변경 | 불변식 |
| --- | --- | --- |
| D8 checkpoint·request·report | 없음 | 확정 손익·배분·counterApplied·적용 당시 epoch/revision/시각의 해시 불변 |
| 과거 source.events·운영비 events·종료 결과 | 없음 | 원본 비용·요율·체결·기간·역사적 HOLD/null 값 불변 |
| 현재 공통 잔액 `handoff.accounts` | 검증된 후속 사건의 차액만 | 단일 초기 현금, 재생한 기준 잔액 + 후속 차액과 일치 |
| 후속 결제 명세·현재 캐시 | 사건 추가와 재생 결과 갱신 | 대상별 적용 1회, 미해결 금액·개수와 합계 대조 |
| 상태 revision/epoch/감사/논리 시계 | 원자 저장·소유권 규칙에 따라 갱신 | 원래 마감 영수증·적용 당시 epoch는 변경하지 않음 |
| 손실 횟수·기존 중지 | 기존 값 보존, 기존 원문 intake의 HOLD 추가만 가능 | 결제 완료로 중지 제거·재개·손실 재적용 없음 |

`seed.ledger.wallets`의 초기 기준 잔액에 차액을 또 쓰면 이중 반영이 되므로 금지한다. D6 `operating.effects`와 옛 원장 재생 값은 **마감 이전 사건의 역사적 합계**로 보존한다. D9의 현재 운영비 paid/payable은 그 기준 합계와 후속 운영비 지급을 합성한 별도 명세로 표시하고, 현재 공통 잔액과 대조한다. 두 값의 시점·역할을 생략한 채 서로 다른 현재 잔액으로 노출해서는 안 된다.

D9를 모르는 보고/내보내기/학습 수용 경로는 새 실행을 명시 거절하거나 지원 불가 HOLD로 반환해야 한다. 옛 source.events만 합쳐 현재 금융 보고가 맞는 것처럼 내보내면 안 된다. 현재 잔액 조회와 원래 마감 결과 조회를 함께 인수하되, 전체 학습·앱 연결은 계속 미지원이다.

## 🧾 사건·식별자·근거 계약

첫 구현은 한 명령당 한 대상을 처리한다. 계획 명령은 `PAY_CLOSED_OBLIGATION`과 `SETTLE_CLOSED_FILL` 두 종류다. 예약 해제·신규 비용 인식·체결·정정 기능을 섞지 않는다.

| 필드군 | 필수 의미·검증 |
| --- | --- |
| 실행 경계 | 확장 계약 해시, TEST_ONLY/SYNTHETIC_FIXTURE, run/configHash, sourceScope, KRW, 원래 closeId/checkpointHash 일치 |
| 대상 식별 | 운영비는 원래 obligationId와 costEventId, 매매는 원래 sourceScope/runId/fillId 및 posting key/identityHash. 원장에 존재하는 미결제 기준점만 허용 |
| 금융 근거 | 당시 확정 receivable/payable 또는 amountKrw, 원본 비용/대상 해시. 외부 입력액은 비교 대상일 뿐 원래 금액을 덮어쓰는 권한이 아님 |
| 업무 사건 | 합성 공급자 범위 + businessEventId + 사건 종류·대상·발생 시각·금액을 고정한 canonical identity. 대상이 달라지거나 동일 ID의 금융 내용이 바뀌면 충돌 |
| 전달·동시성 | commandId, expectedRevision/stateHash. 전달 ID와 업무 ID를 구분하고 최초 영수증에는 원래 입력 해시를 보존 |
| 시각·출처 | occurredAt, availableAt, receivedAt, postedAt, 의미가 고정된 sourceHash. 실제 수신 증명/서명이라고 부르지 않음 |

매매 결제 금액은 매수/매도 방향으로 추정하지 않고, 기존 posting의 `receivable`과 `payable`에서 가져온다. 비용이 매도대금을 초과하는 합성 사례에서는 SELL도 payable일 수 있다. 후속 결제 때 현재 요율을 적용하거나 수수료를 다시 산출하지 않는다. 운영비는 기존 정수 원화 문자열을, 매매는 기존 정확한 10진수 금액 표현을 보존한다. JavaScript Number로 변환하거나 일괄 원 단위 반올림하지 않는다.

업무 동일성 해시의 필드 집합은 확장 버전·실행/configHash·sourceScope·통화·closeId/checkpointHash·명령 종류·대상 식별/원본 해시·businessEventId·occurredAt·금융 금액·sourceHash로 고정한다. sourceHash는 이 업무 증거의 출처를 식별하며 commandId/expectedState/availableAt/receivedAt/postedAt 등 전달·수용 메타데이터를 포함하지 않는다. 동일 업무 재전송의 전달 메타데이터는 최초 영수증을 덮어쓰지 않는다. 전체 요청 해시는 이와 별개로 보존한다.

입력 길이·스케일은 기존 대상 계약의 유효 범위를 넘기지 않고, 원래 금액과 정확히 같은 값을 요구한다. 누계 정밀도는 허용 최대 자릿수·스케일·M에서 산출해 충분함을 검증해야 한다. 기존 전역 Decimal 정밀도40을 근거 없이 충분하다고 가정하거나 변경하지 않는다. 필요하면 D9 안의 국소 정밀도/정수 스케일 계산을 사용하고 큰 원금에 작은 차액을 더하는 경계 시험을 포함한다.

### 두 겹의 중복 방지

1. 같은 commandId·같은 입력이면 원래 영수증을 반환한다. 같은 commandId·다른 입력은 충돌이다.
2. 새 commandId 또는 새 epoch여도 같은 업무 사건·같은 canonical 금융 내용은 원래 영수증 + 현재 상태를 반환하고 새 명령/감사/차액을 쓰지 않는다. 재전송의 receivedAt 등 전달 메타데이터 변화는 업무 동일성을 바꾸지 않는다. 같은 업무 ID의 의미 있는 내용·출처 근거 해시 변경은 충돌이다.
3. 다른 업무 ID를 만들어도 이미 지급/결제한 **대상 자체**를 다시 지급할 수 없다. 첫 구현에는 정정/역분개가 없으므로 이미 해소한 대상의 새 사건은 충돌/검토 대상이다. 마감 전에 이미 결제된 대상도 동일하다.

중복·대상 소비 여부 검사는 메모리 캐시가 아니라 동일 writer 트랜잭션 안에서 검증된 영속 이력과 대조한다. 새 입력은 최신 expectedState가 필요하고, 정확한 재전송은 이전 expectedState여도 원래 영수증을 반환할 수 있다. 요청 유실 후 새 ID를 만들어 성공을 추정하지 않는다. 재조회/재생 검증 없이 중복 성공을 반환하는 빠른 경로도 허용하지 않는다.

## 🕒 시각·지연·미지원 자료

처음 수용하는 사건은 `checkpoint.appliedAt ≤ occurredAt ≤ availableAt ≤ receivedAt ≤ postedAt < followupEndExclusive`를 만족한다. postedAt은 저장 명령에 고정된 합성 논리 시각이며 현재 논리 시계 이상이어야 한다. 실제 lease 만료에 사용하는 Repository 시계와 혼동하지 않는다. 재생 때 현재 벽시계로 postedAt을 다시 만들지 않는다.

늦게 도착한 **마감 이후 결제**는 위 조건과 알려진 대상/금액을 만족하면 허용한다. 서로 다른 대상의 occurredAt 순서가 뒤바뀌어 도착해도 원래 발생 시각을 고치지 않고, 단조로운 postedAt/revision 순서로 반영한다. 반대로 마감 전에 발생했는데 누락됐던 비용/지급 자료, 금액이 달라진 정정, 근거를 확인할 수 없는 자료는 이 계약 밖이다. OC-U05/U07의 소급 정책을 임의 적용하지 않는다.

결제 예정일은 확인된 별도 근거가 있을 때만 표시하고 없으면 unknown이다. D9 첫 구현은 실제 T+n 영업일 계산을 제공하지 않는다. 미해결 기간은 읽기 기준 asOf에서 계산하는 파생 값이며, 하루가 지났다는 이유로 지급·손실·삭제 사건을 쓰지 않는다. 예정일 초과와 검증된 지급 실패는 다른 사실이다. 관찰 구간을 지나도 채무/미수는 남고 미해결/HOLD로 보고한다. **시간 경과는 결제 증거가 아니다.**

정확한 과거 재전송은 원래 수용 당시 시각으로 검증하므로 현재 관찰 구간이 끝났더라도 원래 영수증을 복구할 수 있다. 최초 수용과 재전송 검사를 뒤섞어 이미 성공한 사건을 만료 실패로 바꾸지 않는다.

미지원 자료는 자동 반영하지 않는다. 호출자는 기존 명시 `postCloseInput`의 원문 한도/시각 조건을 지켜 증거를 보존할 수 있다. 이 별도 intake를 호출하지 않았거나 거절됐다면 DB에 보관됐다고 응답하지 않는다. 원문 한도에 걸리면 호출자가 원문을 유지해야 한다. D9의 정상 결제는 기존 RECONCILING/HOLD 중에도 검증된 대상에 한해 허용하되, 원문을 해결 완료로 바꾸거나 기존 HOLD를 지우지 않는다. 원장 변조·불완전 재생은 정상 결제도 차단한다.

**D9 선택 실행에는 추가 원문 시각 가드가 필요하다.** 현재 D8 원문 intake는 observedAt을 seed.clock으로 저장하며 상한이 없다. 그러므로 D9에서는 새 원문도 같은 writer 트랜잭션에서 `observedAt < followupEndExclusive`를 강제하고, 위반 시 시계/원장/감사 불변으로 거절해 호출자가 보존하도록 한다. 종료 시각 이상인 원문 한 건이 정상 결제의 postedAt 조건을 영구 차단하는 것을 막기 위해서다. 구형 D8의 계약은 바꾸지 않는다. 종료 미만으로 시계가 진행된 경우에는 postedAt의 동률을 허용하므로, 더 이른 실제 발생/수신 시각을 가진 유효 결제도 그 현재 논리 시각으로 기록할 수 있다. 원래 수용된 원문의 정확한 재전송은 새 현재 시각으로 다시 쓰지 않는다.

## 🧮 회계 항등식과 검산 자료

마감 이후 열린 포지션·미확정 주문·예약이 없는 첫 범위에서 `C=현금`, `R=미수`, `P=미지급`, `Q=예약`이라 두면 `E=C+R−P`, `가용현금=C−P−Q`다. E는 이 합성 현금성 장부의 대조 값이지 외부 전체 계좌 NAV 인증이 아니다.

- 운영비 a 지급: `C'=C−a`, `P'=P−a`, 발생 비용·E·최종 손익·손실 횟수 불변.
- 체결의 미수 r/미지급 p 결제: `C'=C+r−p`, `R'=R−r`, `P'=P−p`. E와 기존 거래비 불변.
- 미수 수령 전에는 가용 현금에 더하지 않는다. 수령하면 가용액은 r만큼 증가하지만, 거래 허용은 계속 false다. 지급은 현금과 채무를 함께 줄이므로 가용액을 두 번 줄이지 않는다.
- 각 적용 뒤 현금·미수·미지급·가용액 비음수, 대상 잔여액과 합계 일치를 검증한다. 부족·불일치이면 전체 명령을 거절하고 성공으로 기록하지 않는다. 실제 외부에서 이미 발생한 불일치의 자동 보정은 별도 실자료 대사 계약이다.

## 🧱 단일 COMMIT과 재생

한 명령은 다음 순서를 따른다. 네트워크 호출이나 별도 파일 생성을 이 DB 트랜잭션에 넣지 않는다.

1. 입력 크기·엄격한 스키마를 검사하고, 같은 Repository writer 트랜잭션을 연다.
2. 전체 기존 명령/감사/영수증/캐시/체결 인덱스를 재검증한다. D8 경계에서 기준점을 다시 유도하고 이후 후속 사건을 순서대로 재생한다.
3. 확장·실행·마감 해시·업무 중복/충돌·대상 소비 여부를 검사한다. 정확한 재전송은 원래 영수증과 현재 상태를 반환한다.
4. 새 사건이면 expectedState·시각·원금·통화·자원 슬롯을 검사하고, 현재 공통 잔액/대상 잔여액을 계산한다. 체크포인트/손익/카운터 불변을 검증한다.
5. 새 명령·영수증·후속 명세·현재 공통 잔액 캐시·감사를 같은 COMMIT으로 기록한다. 별도 파생 인덱스를 추가한다면 그것도 같은 트랜잭션과 재생 검증 대상이다.
6. writer/epoch/lease를 다시 검사하고 COMMIT한다. 응답 전에 프로세스가 종료되어도 재시작 시 전체가 있거나 전혀 없어야 한다. 롤백 오류가 원래 오류를 은폐해서는 안 된다.

기존 매매 fill index와 과거 승인/원장 내용을 후속 결제에 맞춰 덮어쓰지 않는다. 원래 closeId를 재전송하면 **원래 마감 영수증과 후속 결제가 반영된 현재 상태**를 돌려준다. 현재 상태를 원래 마감 상태로 되돌려서는 안 된다.

### 자원·장애 경계

마감 시 미지급 의무 수 + 미결제 fill 수를 M이라 하면 정상 후속 금융 사건은 대상당 최대1개, 총 M개다. M과 합계는 검증한 기준점에서 산출한다. 기존 매매5,200·운영비100·원문100의 예산을 공유해 정상 결제 슬롯을 소모시키지 않고, 새 확장의 전체 저장/재생 한도에 유한한 M을 반영한다. 원문100개가 가득 차도 이미 확정된 대상의 유효 결제 슬롯은 남아야 한다. 이 제한은 새 매매 한도나 무제한 파일 생성 허가가 아니다.

0원 대상도 슬롯과 고유 ID를 소비한다. 중복/충돌/거절을 새 금융 명령으로 기록해 개수를 늘리지 않는다. 같은 DB와 writer 잠금 아래 경합을 직렬화한다. 레이트 제한/디스크 총량 정책은 아래 외부 연결 선행 인수와 구분한다. 읽기 재생 비용·다중 실행 CPU/디스크 고갈까지 M만으로 해결된다고 주장하지 않는다.

SQLite writer 잠금과 fencing을 사용하지만 **절대 벽시계 만료 전에 COMMIT된다는 보장은 하지 않는다**. 마지막 소유권 검사 뒤 OS 정지가 발생하는 경우까지 별도 시험해야 한다. 다른 writer의 소유권 교체도 동일 DB 쓰기 잠금에 종속되어야 하며, 외부 브로커 주문 같은 DB 밖 부작용은 이 보호만으로 다루지 않는다.

소켓/HTTP 재시도 라이브러리, 게이트웨이, outbox DB를 계약 작성만을 위해 설치하지 않는다. 위 항목은 실제 외부 연결의 선행 조건이지 이번 문서 단계에서 모두 구현한 기능이 아니다.
