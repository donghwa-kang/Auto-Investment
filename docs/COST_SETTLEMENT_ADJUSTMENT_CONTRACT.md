## 💰 부분 결제 계약 — 다음 합성 구현 범위

### 기준점·대상·정확한 산술

원래 대상 집합 M과 각 대상의 원본 해시는 D8 마감 COMMIT에서 고정한다. `originalReceivable/originalPayable`, `settledReceivable/settledPayable`, `remainingReceivable/remainingPayable`, 마지막 적용 revision을 분리한다. 현재 잔여액을 새 원금으로 덮어쓰지 않는다. 운영비의 incurred는 불변, paid는 실제 지급 누계, payable은 잔여액이다.

한 사건은 **한 알려진 대상**의 증분 수령 r/지급 p다. `0 ≤ r ≤ remainingR`, `0 ≤ p ≤ remainingP`, `r+p>0`이어야 한다. 체결 방향으로 부호를 추측하지 않고 원래 posting을 사용한다. 누적 입금액을 증분으로 해석하거나 여러 체결을 임의 배분하지 않는다. 증분을 증명할 수 없는 누적 명세는 보류한다.

열린 포지션/예약 없는 현재 범위에서 `E=C+R−P`, `Available=C−P−Q`, Q=0이다. 부분 결제도 `C'=C+r−p`, `R'=R−r`, `P'=P−p`이며 E는 불변, Available은 r만큼 증가한다. 현금·잔여 미수/미지급·가용액은 비음수여야 한다. 이미 원장에 인식한 비용을 지급할 때 손익에 다시 쓰지 않는다.

상태는 잔여액과 근거로 산출한다. 양수 대상은 아직 지급 0이면 OPEN, 일부 후 잔여 양수면 PARTIAL, 양쪽 잔여 0이면 SETTLED다. 원래 양쪽 0인 대상은 증거 있는 `CONFIRM_ZERO_TARGET`을 정확히 한 번 처리하며, 임의 0원 부분 사건으로 이력을 채우지 않는다. 이 예외도 명시 슬롯과 업무 식별자를 소비한다.

운영비 금액은 기존 30자리 이내 정수 원화 문자열, 체결 금액은 정수60/소수40자리 이내 문자열을 유지한다. 지수 표기·NaN·음수·Number 변환·자동 반올림은 금지한다. 금융 동일성 해시에는 정규화한 정확한 수치를 쓰고, 전체 요청 해시에는 원래 입력을 보존한다. 따라서 새 전달 ID의 1/1.0 금융 값은 같을 수 있어도 같은 commandId의 원문 변경은 충돌이다. 전역 Decimal 설정은 변경하지 않는다.

### 제안 입력과 중복 방지

| 필드군 | 필수 내용 |
| --- | --- |
| 범위 | 새 contract/configHash, TEST_ONLY/SYNTHETIC_FIXTURE, sourceScope, KRW, 원래 closeId/checkpointHash |
| 대상 | 원래 targetKey·originalHash, 증분 r/p 또는 0원 확인 종류 |
| 업무 근거 | businessEventId, 안정적인 `sourceEventKey`, sourceHash, occurredAt |
| 전달/동시성 | commandId, expectedRevision/stateHash, availableAt/receivedAt/postedAt |

`sourceEventKey`는 합성 공급자 범위+불변 지급/이체 ID(+필요한 고유 행 ID)다. 문서 재발행·재다운로드로 바뀌는 문서 ID, commandId·수신 시각·무작위 재시도 ID로 만들지 않는다. 원천 문서 ID/버전은 별도 근거 참조로 보존한다. 한 원천 지급 행을 다른 업무 ID로 포장해도 다시 쓸 수 없어야 한다. 같은 금액의 정당한 두 지급은 서로 다른 원천 지급 식별자일 때만 구별할 수 있다. 실제 공급자가 이 식별자를 제공한다는 가정은 하지 않는다.

D10-B는 원천 지급 식별자·대상·종류·증분 금액·발생 시각·근거 해시의 **고정된 합성 증거 목록**을 별도로 받아 초기 설정 해시에 묶는 검증용 경계를 둔다. 원장 사건에서 목록을 역으로 생성하거나 요청의 `verified=true`를 믿지 않는다. 목록은 최대15,900행·고유 원천 키·엄격한 필드/문자열 길이로 제한하고, 새 사건은 목록의 정확한 행과 일치해야 한다. 재시작 때 다른 목록을 주입하면 거절한다. 이는 독립 준비된 fixture를 대조하는 장치일 뿐 실제 서명/공급자 진위·누락 없음 증명은 아니다. 목록 고갈/증거 부족은 명시 HOLD다.

목록의 대상은 원래 obligationId 또는 runId/fillId로 참조하고, 아직 만들어지지 않은 checkpointHash·전체 configHash·목록 자신의 해시를 행 안에 넣지 않는다. 순환 해시 없이 목록 해시를 설정에 포함하고, 수용 시에는 실제 마감의 targetKey/originalHash와 추가 대조한다. ID는 기존 대상별 ID 스키마, 시각/금액은 D9 한계, sourceEventKey/sourceHash는 64자리 소문자 SHA-256 표현을 재사용한다. sourceEventKey의 해시 전 입력 필드·정렬도 계약 버전에 고정하며 공급자 인증으로 해석하지 않는다.

금융 canonical에는 계약/실행/계정/통화/마감, 종류·대상 원본 해시·정규화 r/p, sourceEventKey/sourceHash/occurredAt을 포함한다. businessEventId는 별도 고유 인덱스다. 전달 ID·시각·expectedState·현재 epoch와 향후 관찰 창 ID는 금융 동일성에서 제외한다. 새 창이나 새 businessEventId가 같은 지급을 새 금융 사건으로 만들 수 없다.

1. 이미 저장된 commandId는 epoch 정규화 외 **전체 원래 요청**이 같아야 최초 영수증을 복구한다. 바뀌면 충돌이다.
2. 같은 businessEventId 또는 sourceEventKey를 찾으면 금융 canonical이 같을 때만 최초 영수증+현재 상태를 반환한다. 두 키가 서로 다른 기존 사건을 가리키면 충돌이다. 별칭 business ID를 추가 저장해 중복 이력을 늘리지 않는다.
3. 다른 지급 증거라도 대상 잔여액 초과는 거절한다. 대상별 residual과 증거 소비는 같은 영속 명령 이력에서 재생한다. 내용 해시만으로 서로 다른 실제 지급을 합치지 않는다.
4. 정확한 중복은 최신 상태·기간·용량 검사보다 먼저 판정하되, writer 소유권·엄격한 범위 검사와 전체 이력 검증을 생략하지 않는다. 새 요청에는 최신 expectedState가 필요하다.

중복 조회에만 사용한 새 command/business ID를 영속 별칭으로 무한 저장하지 않는다. 반환값은 최초 영수증의 원래 command/business ID를 명시하고, 새 별칭이 예약됐다는 보장을 하지 않는다. 호출자는 그 원래 ID/요청으로 복구한다. 실제 통신 계층에서 모든 전달 ID를 영구 예약하려면 별도 유한 outbox/중복 보존 계약이 필요하다.

두 프로세스가 R=100에 각각 r=60을 제시하면 첫 60만 반영된다. 둘째는 stale 상태로 거절되고 최신 상태로 다시 보내도 남은40 초과로 거절된다. 둘째를 임의40으로 잘라 성공시키지 않는다. 명령이 거절됐다고 원천 증거가 자동 보관됐다고 응답하지 않는다.

### 시각·자원 예산

D10-B의 최초 수용 시각은 D9처럼 `마감 ≤ occurred ≤ available ≤ received ≤ posted < followupEndExclusive`, posted ≥ 현재 논리 시계다. 마감 전 누락 비용/결제는 이 범위 밖이다. 원문 intake도 같은 종료 상한을 유지하며 원문100개와 금융 사건 슬롯은 분리한다.

**첫 합성 검증용 제안 상한**은 대상당 미완결 부분 사건 최대2개와 잔여 전액 종료 슬롯1개다. 세 번째 부분 사건은 거절하되 잔여 전액 결제는 허용한다. 첫/둘째 사건으로 전액 종료하면 남은 슬롯을 다른 대상이나 원문으로 넘기지 않는다. M≤5,300이면 총 금융 사건≤3M≤15,900이다. 0원 대상은 종료 슬롯1개만 쓴다. 관찰 이관·재시작·새 ID로 이 상한을 초기화하지 않는다.

이 상한은 시장에서 세 번만 입금된다는 가정이나 실자료 운영 한도가 아니다. 상한 밖 분할이 관측되면 남은 채권/증거를 보존하고 HOLD한다. 실제 연결 전에 최대 이력 Store 부하·수신 보존·검토 처리량과 별도 유한 한도를 인수해야 한다. 합성 상한을 운영에 그대로 적용하면 정상 결제를 막을 수 있다.

각 대상 누계가 원금을 넘지 않으므로 최대 금융 총액은 M개의 원금 합으로 제한된다. 사건 누계의 보수적 자릿수 여유도 `100 + ceil(log10(15,900)) < 128`로 대조한다. 국소 정밀도128 또는 정확한 정수 스케일 계산을 사용할 수 있지만 매 결과의 정수60/소수40자리 한도를 검사한다. 산술 검산은 최대 Store 부하 인수가 아니다.

## 🧾 조정 슬롯 — 정책 선택 후 구현할 제안

### 부분 수령과 비용의 구별

| 근거 | 예: 원래 미수100 | 처리 |
| --- | --- | --- |
| 특정 대상의 99 수령만 확인 | 미수1이 남음 | RECEIVE99, E 불변. 이유 불명1을 비용으로 만들지 않음 |
| 새 수수료1과 총액100/순액99 상계가 각각 확인 | 미수100·새 비용1·입금99 | 아래 원자 순액 사건. E는1 감소 |
| 수수료1이 이미 채무로 인식됨 | R100/P1에서 순액99 확인 | 기존 P1과 R1 상계 + R99 수령. E 불변, 비용 재인식 금지 |
| 계좌 현금 숫자만99 증가, 대상/성격 불명 | 입금 매칭 불가 | 원문·불일치 진단 보존, 금융 성공 아님 |
| 승인자가 “소액이니 맞춰”라고만 입력 | 추가 근거 없음 | 원장 반영 거절. 승인 자체는 지급/비용 증거가 아님 |

아래 제안 슬롯은 임의 `deltaEquity` 숫자를 받는 만능 API가 아니다. 합성 manifest로 원인·원본·전후 총액·미인식 여부를 검증하는 타입별 명령으로 설계한다. 실제 공급자 검증기는 별도 인수다.

| 제안 사건 | 금융 효과 | 중복/원인 제약 |
| --- | --- | --- |
| `RECOGNIZE_PROVEN_CHARGE(f)` | P+=f, E−=f. 지급 전에도 비용 반영 | 양수 f, 고유 charge/증거 ID, 종류(거래비/운영비)·귀속 대상·기간 필수. 기존 인식 항목을 다시 생성 금지 |
| `CREDIT_UNPAID_CHARGE(g)` | 해당 P−=g, E+=g. 현금 이동 없음 | 확정 취소/감액 근거, 연결된 미지급 의무의 잔여액 이하 |
| `RECOGNIZE_REFUND_RECEIVABLE(g)` | R+=g, E+=g. 아직 현금 아님 | 이미 지급한 비용의 환급 채권 확인. 누적 감액/환급은 검증된 유효 원비용을 넘지 않음 |
| `SETTLE_ADJUSTMENT_TARGET(r,p)` | C+=r−p, R−=r, P−=p, E 불변 | 앞의 조정으로 만든 알려진 대상만 결제. 실제 이체 근거 필요 |
| `APPLY_PROVEN_NET_SETTLEMENT` | 명시한 gross R/P, 상계, 현금·필요한 새 비용을 단일 COMMIT | 총액/순액·상계 권리/대상 근거가 함께 있어야 함. 순액으로 총비용 역산 금지 |

기존 D9 command에 이 종류를 추가하지 않는다. 별도 합성 조정 계약/승인 해시가 있는 실행에서만 허용할 제안이며, D10-B에는 전부 제외한다. 종목 수익을 좋게 보이게 할 임의 수익·채권 상각, 미확인 세금/환율 추정, 역분개·새 체결·취소 후 재거래는 여기서도 정의하지 않는다.

### 순액과 정정 버전

R100에서 새 비용1이 확인된 순액99 수령은 내부적으로 `P+1 → R−1/P−1 상계 → C+99/R−99`다. 세 효과를 모두 같은 COMMIT에 반영한다. 중간 상태를 보고/신규 진입에 노출하지 않는다. 이미 P1이 인식됐다면 첫 비용 인식은 생략하고 **기존 의무 ID를 소비**한다. 원천 한 행을 부분 수령과 순액 사건 양쪽에 쓰지 못하게 sourceEventKey와 관련 증거 행 소비를 함께 검사한다.

정정은 `adjustmentId, revisesId, supersedesReportHash, priorEconomicHash, reasonCode, evidenceHash, approvalHash`의 연결을 가진다. 새로 받은 절대 총액을 차액으로 그대로 더하지 않고, 검증한 이전 총액과의 차이를 타입별로 계산한다. 같은 원본의 상충하는 두 정정은 최신 revision에서 재검토한다. 증거/승인 변경을 새 business ID로 숨기거나 과거 charge·paid 값을 직접 음수로 덮지 않는다. 미래 권한 모델 없이 approvalHash만 맞춰 통과시키지 않는다.

### 금융 사실과 보고/위험 판정

발생 시각, 실제 이용 가능 시각, 수신/반영 시각, 경제적 귀속 기간을 별도 보존한다. 늦은 비용의 occurredAt이 마감 전일 수 있으므로 D9의 시각 조건을 조용히 풀지 않고 조정 계약에만 별도 규칙을 둔다. 최초 승인·원래 특징/라벨·D8 체크포인트·그때의 손실 카운터는 불변이다.

제안 보고는 `originalClose`, `currentAccounts`, `adjustmentLedger`, `restatedReportVersion`, `attributionStatus`, `riskReviewRequired`를 구분한다. OC-U05/U07 미결정 중에는 최종 재배분/최종 수정 손익을 null로 남기고 HOLD한다. 확정 비용의 현재 E 영향과 미확정 보고 배분을 혼동해 E 반영을 미루거나 배분 시 두 번 빼지 않는다. 과거 중지 위반 가능성이 발견되면 현재 검토 중지를 유지하고, 유리한 정정도 기존 중지를 자동 해제하지 않는다.

향후 재판정은 원래 청산 순서와 원래 시작 카운터에서 별도 버전으로 재생해야 한다. 현재 카운터에 과거 손실을 다시 더하거나 구형 보고의 해시를 수정하지 않는다. 학습으로 내보낼 때도 원래 as-of 자료와 새 정정 라벨의 이용 가능 시각/버전이 분리되어야 한다. **그 자동 적용/해제·학습 계약은 아직 미결정이다.**

확인된 실제 비용이 현재 Available을 음수로 만들 수 있다는 경우도 구분한다. D9/D10-B의 비음수 합성 결제 가드는 그대로다. 미래 실자료 장부는 확인된 채무를 삭제하거나 0으로 잘라 숫자를 맞춰서는 안 되며, 음수 가용액/부족을 표현하고 신규 위험을 금지하는 별도 계약이 필요하다. 이 표현을 아직 구현하지 못한 상태에서는 원문 보존 + 대사 미완료로 보고하며 현재 수치가 외부 잔액과 일치한다고 인증하지 않는다.

## 🕒 관찰 기간 밖 미결제 이관 — 후속 설계

권장안은 **같은 DB, 같은 초기 현금, 같은 금융 사건 이력에서 관찰 창만 연결**하는 것이다. 새 위험일/실행 계좌 생성이나 현금 이체가 아니다. 원래 followupEndExclusive·D8 해시·구형 사건을 바꾸지 않는다. 원래 D9 실행에 이 능력을 사후 활성화하는 것은 지원하지 않는다.

향후 새 합성 확장을 처음 만들 때 관찰 창 연결 능력·유한 lifetime 상한을 전체 설정에 선언한다. 첫 시험 제안은 초기 창+후속 창1개뿐이다. 이 숫자는 운영 정책이 아니며 이후 무제한 갱신을 허용하지 않는다. D10-B에서는 창 연결을 아직 제공하지 않는다.

제안 `CONTINUE_SETTLEMENT_WINDOW`는 다음을 같은 writer COMMIT에 기록한다.

1. 기존 창 종료 이후임을 확인한다. `postedAt ≥ oldEndExclusive`, `postedAt ≥ seed.clock`, `newStart=postedAt < newEndExclusive`. 다음 창이 기존 창과 겹치거나 미래 창을 미리 활성화하지 않는다.
2. 전체 재생으로 현재 잔액·원대상/잔여액·미해결 증거 참조·HOLD·중복 인덱스·남은 lifetime 슬롯을 검증한다. 직전 revision/hash와 해당 prefix를 봉인한다. 봉인하는 명령 자체를 포함하지 않는 prefixHash로 순환 참조를 피한다.
3. 새 관찰 windowId/순번·이전 windowId/봉인 해시·승인 근거·새 유한 구간을 append한다. 현재 잔액과 E/가용액 변화는 **0**이다. 기존 잔액을 별도 openingCash로 다시 더하지 않는다.
4. 잔여 대상은 원래 targetKey를 유지한다. 새 창은 조회 인덱스일 뿐 새 지급 대상/중복 키가 아니다. raw100·대상별 부분 슬롯·업무 식별자 예산을 초기화하지 않는다.

새 창에서 처음 반영하는 알려진 결제는 `원래 마감 ≤ occurred ≤ available ≤ received ≤ posted`, `newStart ≤ posted < newEnd`를 검사한다. 발생/수신이 이전 창이나 공백에 있어도 원래 사실 시각을 유지한다. 이를 새 창 발생으로 바꿔 적지 않는다. 공백 중 자동 수집/완전성은 주장하지 않으며 원문이 유실됐다면 완전성 HOLD를 유지한다. 마감 전 누락은 이 창 연결로 수용하지 않고 조정/대사 계약으로 보낸다.

원래 창의 정확한 중복은 종료 후에도 최초 영수증을 반환한다. 창 이관과 지급 경합은 같은 writer 직렬화와 expectedState로 처리한다. 두 이관이 경합하면 단 하나의 후속 창만 생기며, 같은 이관 ID의 다른 종료 시각/근거는 충돌이다. 원래 마감 재전송은 원래 영수증과 최신 상태를 반환한다.

창이 끝나거나 이관 상한에 도달해도 채무는 OPEN/PARTIAL로 남는다. `observationEnded`, `continuationUnavailable`, `reconciliationRequired`를 별도 표시하고 예정일은 증거 없으면 null이다. 종료를 연체·파산·상각·수익/손실로 추정하지 않는다. 장기 보존·아카이브/두 DB 간 인계는 별도 계약이며 기록을 삭제해 공간을 확보하지 않는다.

## 🔒 저장·복구와 미지원 증거 보존

원자 경계는 기존 Repository의 writer/epoch/lease와 같은 단일 COMMIT이다. 새 명령, 증거 소비/잔여액, 현재 현금·미수·미지급, 조정/창 연결 명세, 영수증·감사·현재 상태 캐시를 함께 저장한다. 조정 복합 사건의 일부만 커밋하거나 먼저 메모리에 완료 표시하지 않는다. 네트워크 호출/외부 승인을 DB 잠금 안에서 기다리지 않는다.

재생은 기준점에서 모든 사건을 다시 계산하고 캐시·파생 인덱스와 대조한다. 단계별 쓰기 실패·SQLite FULL·COMMIT 전후 프로세스 종료·epoch 교체·중복 재전송은 별도 무실패 golden과 비교해야 한다. 원래 오류와 rollback 오류를 함께 보존한다. lease가 물리적인 스토리지 쓰기를 정확한 벽시계에 중단시킨다고 주장하지 않는다.

제품 HTTP/outbox는 여전히 미구현이다. 합성 복구 검사는 발송 전에 원래 명령 ID/본문/expectedState를 시험 소유 파일에 보존하고 새 프로세스가 그것만 읽어 복구하도록 한다. 이 시험을 영구 outbox·전원 차단 내구성·사용자 승인 증명으로 부르지 않는다.

스키마 거절·기간 만료·raw 포화는 **금융 반영 없음 / 원문 저장 여부 / 재시도 가능 조건**을 구분해 응답할 설계다. 별도 원문 intake 실패 시 호출자가 원문을 보유해야 한다. 용량 부족 상황에서 무한 재시도/새 run 생성으로 우회하지 않는다. 계정/다중 run 총량·파일 생성/인증 Rate Limit·OS 격리는 별도 운영 인수다.
