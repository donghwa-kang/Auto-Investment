# 모의매매 통신 검사 경계

_테스트 구조 결정 및 재현 안내 · 제품 동작 변경 없음 · 2026-09-17_

## 📋 수정 이유

이전 `NETWORK-01`은 합성 엔진을 실행한 뒤 `src/core`·`src/server` 전체에서 통신 관련 문자열을 검색했다. 독립 [분석 모형 worker](../src/server/analysis-process-worker.ts)의 금지 모듈 목록과 차단된 `fetch` 자기검사가 검색에 걸렸다. 반대로 `fetch`를 다른 변수에 넣어 호출하는 별도 토스 수집 구현은 해당 정규식으로 찾지 못했다.

문제는 기존 운영비 계산의 통신 추가가 아니라 검사 대상과 방법의 불일치였다. 당시 198/199 결과는 [진행 기록 · 공개 요약](PROJECT_STATUS.md)에 보존한다. 이번에는 제품 `src`, 원본 정책, 상품 허용 범위, 의존성, 계좌/주문 경로를 수정하지 않는다.

## 🎯 결정과 검사 범위

전체 폴더 문자열 검색을 **실행 계측과 전이 의존성 검사**로 분리한다. 특정 파일만 예외로 추가하는 방법은 별칭 호출과 worker 누락을 해결하지 못하므로 사용하지 않는다. 임의 JavaScript를 완전히 분석하는 도구나 OS 방화벽을 새로 구현하는 범위도 아니다.

| 경계 | 검증 방법 | 증명하지 않는 범위 |
| --- | --- | --- |
| 합성 엔진 시작·전진 | `NETWORK-01`의 부모 fetch/https 계측 | import 시점·worker 전체 통신 |
| 모의매매 판단·실행 구현 | `BOUNDARY-01`과 반례의 빌드 AST 검사 | 외부 패키지 내부·임의 코드 우회 |
| 독립 분석 모형 | `PROCESS-01/08` 등 제한 프로세스 시험 | 악성 모형·OS egress 격리 |
| 실제 자료 수집 모듈 | 파일을 실행하지 않는 탐지 반례 | API 이용 권리·요금·자료 품질 |

[정적 검사기](../tests/network-boundary.ts)는 빌드된 JavaScript를 읽기만 한다. 루트는 `Engine`, 평가 worker, `PortfolioPaperEngine`, 생성자로 주입되는 `PortfolioProgram`, 웹용 프로그램/엔진 생성부다. 타입 전용 import는 빌드에서 사라지므로 주입된 판단 구현과 URL로 실행하는 평가 worker를 명시적으로 포함한다. 이 루트 및 정적 import·재수출로 도달하는 프로젝트 모듈을 검사한다.

등록된 정책/합성 JSON은 `type: "json"` 선언과 JSON 구문을 확인한다. 데이터는 코드로 실행하지 않는다. 정책 원본 37개는 `verify:originals`, 합성 프로필 변경 여부는 이번 시작 파일 해시와 별도 대조한다. 37개 원본 검사에는 프로필·픽스처가 포함되지 않으며 JSON 구문 검사도 데이터 전체의 원본 보존을 증명하지 않는다. 누락·허용 경로 이탈·심볼릭 링크·미등록 확장자는 성공으로 넘기지 않는다.

다음 변경은 재검토가 필요하도록 시험을 실패시킨다.

- `fetch`, `WebSocket` 등 통신 기능의 직접 사용 또는 값 참조, 전역 객체 별칭·계산 속성 접근
- 미등록 외부 패키지/하위 경로, 통신 모듈, 동적 import, `require`·내장 모듈 로더
- `TRADING_MODE`·`LIVE_ENABLED` 읽기 이외의 process 접근, 환경변수 객체 별칭·쓰기·삭제
- 고정 평가 worker 이외 생성, 진입점·옵션·관련 import 바인딩 변경
- 누락된 모듈, 잘못된 구문, 승인되지 않은 데이터 import

주석·설명 문자열에 금지 단어가 있는 것만으로 실패하지 않는다. 다만 범용 의미 분석기가 아니므로 실제 사용하지 않는 금지 식별자도 보수적으로 거절할 수 있다. 정상적인 구조 변경이라도 허용 목록을 넓히기 전에 독립 검토와 반례 추가가 필요하다.

## 🔧 로컬 재현

[README 실행 환경](../README.md)의 의존성이 설치된 프로젝트 루트에서 먼저 빌드한다. 오래된 `dist`만 검사한 결과를 최신 소스 검증으로 사용하지 않는다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/network-boundary.test.js dist/runtime/tests/resilience.test.js dist/runtime/tests/analysis-process.test.js
```

정상 조건은 빌드 종료 0과 시험 실패·취소·건너뜀 0이다. 구조 반례는 메모리 문자열 또는 기존 빌드 파일을 읽어 검사하며 API를 호출하지 않는다. 실행 시험은 메모리/새 임시 합성 DB와 직접 생성한 시험 자식만 사용한다. 독립 분석 프로세스는 기존 구현의 Windows·Node 24.20.0 제약을 그대로 적용한다. 사용자 키나 장부를 지정하지 않는다.

이전 비용 연결의 관련 회귀도 함께 확인한다. 상세 명령·로그·중간 실패와 최종 결과는 [PROGRESS · 공개 요약](PROJECT_STATUS.md)의 이번 작업 기록과 `work/network-boundary-verification/`에 보관한다. 제품 CLI, UI, 설치 절차나 사용자 서버 시작·중지 방법은 달라지지 않았다.

## ⚠️ 한계와 다음 작업

이는 **프로젝트 소유 코드의 통신 능력 추가를 탐지하는 한정된 회귀 검사**다. 허용 패키지 내부, 실행 중 임의 주입 객체, HTTP/CLI 부트스트랩 전체, 다른 감독 worker, OS 수준 네트워크 파일 접근·DNS·IPC·악성 코드 우회는 전체 검증 범위가 아니다. 부모 계측의 호출 0이나 모형이 반환한 `externalCalls: 0`만으로 모든 프로세스의 외부 통신 부재를 보장하지 않는다.

독립 분석 모형의 신뢰 경계는 계속 `TRUSTED_MOCK_NOT_OS_SANDBOX`다. 실제 OS 격리·복구, 유료 모델, 실제 계좌·실주문·투자 성과를 검증하거나 활성화하지 않는다. KRX는 향후 자료 공급원 검토 후보로 남으며 연결·다운로드하지 않는다.

후속 투자 기능은 [운영비 연결 안내](investment-data-contract-v1/OPERATING_COST_ESTIMATION_STAGE1.md)의 미결정 비용 처리와 [자료 수용 계획](investment-data-contract-v1/ACCEPTANCE_PLAN.md)에 따라 별도 단계로 진행한다. 이번 검사 통과를 실자료 백테스트 완료나 실전 준비 완료로 해석하지 않는다.
