후속 S9-B 구현·실제 API/검사/한계는 [합성 이력 연결 사용법](COST_HISTORY_ADMISSION.md)과 최신 [PROGRESS · 공개 요약](PROJECT_STATUS.md)를 따른다. 아래 ‘미구현/계획’과 기존 경계 probe는 S9-A 작성 시점의 기록이며 소급해 시험 결과를 바꾸지 않는다.

## 📋 결론과 결정 범위

다음 S9-B는 **새 명시 KRW 합성 실행의 첫 후보**에 완료20위험일 운영비 이력을 연결한다. 비용 추정기는 재사용하고, 신호 선택 → 후보 심사 → 로컬 예약 → 합성 접수 직전 재검사에 같은 근거를 전달한다. 현재 실행의 첫 운영비 사건 이후 신규 진입 HOLD는 유지한다. 계속 매수하는 기능이나 다일 자동 운용을 구현하는 단계가 아니다.

이 문서는 [D03 잔여 연결 지도](D03_INTEGRATION_ACCEPTANCE.md)의 S9-A 결과다. 원본 거래 정책, [운영비 명세](investment-data-contract-v1/OPERATING_COST_SPEC.md), [U08-A/U06-A 결정](OPERATING_COST_INTEGRATION_DECISIONS.md)을 바꾸지 않는다. 새로운 정책 선택 없이 가능한 좁은 시험 범위를 택했으며, 아래 인수 HA-01~16은 **다음 구현에서 실행할 조건**이다. 현재 기능·검사와 혼동하지 않는다.

범위 선택의 결과는 다음과 같다.

- 채택: 기존 추정기를 명시적으로 연결하는 1위험일·단일 KRW·단일 신호의 합성 경로
- 후속: 현재 비용 사건 이후 연속 후보 심사, 부분 이력, 월중 누계 이관, 다일/외화/정정·환불, 학습 입력
- 제외: 실제 자료/API/키/계좌, 새 지출·유료 AI·실주문, 사용자 DB 이관, UI, S7+D9/D10

## 🎯 최소 합성 범위와 미확정 정책

### 당월 누계 0원과 충돌하지 않는 시험

V4의 `priorMonthIncurredKrw`/`priorMonthReservedKrw`는 **이 실행 전에 당월에 발생/예약한 값**이며 현재 0원만 지원한다. 같은 계좌의 월중 발생액이 있는 이력을 넣으면서 이 값을 0원으로 유지하면 월 비용 한도 근거가 불완전해진다. 20일 창의 O를 당월 누계로 복사하는 것도 잘못이다. 두 기간이 다르고, 월 후반에는 20일 창 밖 당월 비용도 있을 수 있다.

첫 S9-B 지원 fixture는 다음과 같이 한정한다.

1. 위험월 첫 위험일의 새 합성 실행. 예: `2026-09-01 09:45 KST`에 시작하면 완료 창은 `[2026-08-12 09:00, 2026-09-01 09:00)`이다. 주말을 포함한다.
2. 그 창 안의 확인된 합성 KRW 비용과 고유 완료 의도만 제공한다. N>0이고, 미래 증가분은 확인된 `"0"`이다. 자료 완전성 선언은 현재 시각 이하에 가용해야 한다.
3. 실행 전 당월 발생/예약은 알려진 0이고, 과거 미수·미지급·미해결 예약·주문·중지 이월을 지원하지 않는다. 과거 O/N은 추정용 원자료이며 과거 계좌를 수입하는 기능이 아니다.
4. 실행 초기 자금은 기존 명시 합성 seed 하나다. 과거 비용 O를 다시 차감하거나 과거 완료 거래 N을 현재 위험일의 거래 수·연속손실에 넣지 않는다. 과거 중지·의무가 없는 새 시험이라는 한계를 표시한다.

이는 **월초에만 실제 거래하라는 정책이 아니라 첫 개발 시험의 범위**다. 실제로 20일을 기다리거나 사용자에게 계좌/비용 이력을 요청할 필요는 없다. 날짜를 이동할 때 신호 봉·세션·호가·요율·예측 가용시각도 일관된 새 합성 자료로 구성해야 하며, 기존 fixture의 결과/해시를 덮어쓰지 않는다.

월중 일반화는 당월 전체 발생/예약 근거 및 미해결 이월과 위험 스냅샷 계약이 필요하다. 이번에는 V4의 0원을 비영으로 풀거나 시작일만 바꿔 기존 중지를 초기화하지 않는다.

## 🔗 원자료 전달과 검증 계약

### 다섯 종류의 비용을 구분

| 종류 | 판단/장부 영향 | 금지할 혼동 |
| --- | --- | --- |
| 과거 O/N의 후보 추정 | 경제성 C와 비용 후 q05에 한 번 반영 | 현재 비용 의무·지급·예약 생성 금지 |
| 현재 발생 의무 | V4의 E·채무에 한 번 반영 | 마감까지 인식 미루기 금지 |
| 현재 현금 지급 | 현금/채무 감소 | 동일 비용 재인식 금지 |
| 현재 미래 지출 예약 | 기존 X/가용현금 반영, 해당 의무 전환 시 상계 | 후보 추정을 예약으로 사용 금지 |
| 현재 기간의 마감 배분 | 확정 O를 완료 거래에 귀속 | 후보 평균을 확정 손익·학습 라벨로 복사 금지 |

같은 q·가격의 `C_stop`, R0, 매수 예약금에 추정 운영비를 추가하지 않는다. 비용 때문에 최종 선택 q가 달라질 수는 있으므로 ‘수량이 언제나 같아야 한다’고 검사하지 않는다. 금액은 기존 검증된 Decimal/정수 스케일 경계를 재사용하며 Number 금액 변환이나 임의 허용 오차로 맞추지 않는다.

### 신호부터 접수까지

아래는 새 연결의 의도이며 공개 API가 아니다. 정확한 필드명은 S9-B에서 확정하되 기존 필드의 의미·구형 해시는 보존한다.

1. **명시 opt-in:** 새 확장 계약/해시와 신호 근거를 결합한다. 이력 원자료는 `OPERATING_COST_TEST_HISTORY_V1`의 strict 검증을 재사용한다. 기존 D6의 무비용 admission 선언을 몰래 다른 의미로 바꾸지 않는다. 확장 미지정 시 기존 무비용 경로가 동일하게 동작해야 한다.
2. **신호/심사:** 당시 이용 가능했던 원자료를 전달하고 현재 configHash·위험 epoch·완료 창·coverage·비용/의도 ID를 검증한다. O/N/추정액/근거 hash를 함께 결합한다. `complete=true`는 합성 선언일 뿐 실제 원천 완전성 인증이 아니다.
3. **예약:** `evaluateLocalProposal` → `evaluateCostSizing`에 같은 이력을 전달한다. 발급된 미수정 receipt만 받으며 COMMIT 직전 현재 상태·epoch·동일 근거를 다시 검사한다. 원자료, 추정 binding, 후보, 현금/위험 예약, 감사는 기존 단일 저장 경계를 사용한다.
4. **접수 직전:** 호출자가 별도로 전달한 현재 원자료를 검사한다. 저장된 승인 이력을 최신 자료처럼 fallback하지 않는다. 자기 미접수 예약·의도만 빼는 기존 재검사를 유지하며 원래 signalAt/TTL·호가/요율/시나리오 TTL을 연장하지 않는다.
5. **동등성:** 별도 현재 원자료의 정규화 binding과 추정액이 승인 시점과 일치해야 한다. 같은 금액이라도 O/N·ID·가용시각·창·설정/epoch가 달라지면 접수를 거절한다. 예: O10/N3와 O11/N3는 모두4원이지만 같은 근거가 아니다. 동일 레코드 중복/순서 변경은 기존 정규화 기준대로 처리한다.
6. **접수 거절:** 기존 예약과 원승인을 보존하고 명시 RELEASE_LOCAL만 허용한다. 새 ORDER/FILL·예약 자동 반환·단일 승인 제한 우회·신규 실행으로 중지 리셋을 하지 않는다. 이미 성공한 동일 명령 재전송은 원래 영수증으로만 복구한다.
7. **재생/보고:** RESERVE/HANDOFF의 원자료는 직렬화 가능한 명령 근거로 보존한다. DB 재열기와 메모리 export 독립 재생에서도 당시 자료를 사용한다. 재생에 저장 자료를 사용하는 것과 새 접수의 ‘현재 증거’로 재활용하는 것은 다르다. 원자료 누락/변조는 실패하며 새 계약을 구형 export에 억지로 넣지 않는다.

새 입력의 개수·금액/ID/직렬화 크기는 기존 이력 한도 및 명령/재생 자원 한도와 함께 검증한다. 초과는 쓰기 전 거절하며 임의 잘라내기·부분 수용·검사 생략을 하지 않는다. raw 입력을 타입 단언이나 수동 candidate 금액으로 우회할 수 없어야 한다.

### 미래정보·재시작·보호

- `occurredAt/closedAt ≤ availableAt ≤ coverage.availableAt ≤ 판단 시각`, 정확한 반열린 완료 창을 검사한다. 현재 위험일의 비용·완료를 과거 O/N에 끼워 넣지 않는다.
- 고정된 미래 청산 손익·최종 마감 배분·나중 수신된 공시/요율을 후보 원자료로 쓰지 않는다. 이 단계의 gross/q05는 합성 시나리오이지 학습된 수익 분포가 아니다.
- 재시작/owner epoch 교체 뒤 과거 원자료의 riskEpoch를 자동 덮어쓰지 않는다. 과거 원장 읽기/동일 명령 영수증 복구와 새로운 승인 발급을 구별한다. 새 접수는 기존 신선도·epoch 검증을 통과하지 못하면 보류한다.
- 첫 현재 운영비 사건 이후의 `OPERATING_ADMISSION_INTEGRATION_PENDING`, 비용 확정 대기, 다른 HOLD/HALT, UNKNOWN은 유지한다. PAY·RELEASE·마감이나 새 이력 공급만으로 해제하지 않는다.
- 이미 합성 접수된 주문의 유효 체결·취소·손절/목표/시간 청산·지급은 이력 공급 실패나 AI 응답을 기다리지 않는다. 보호 루프에 매 tick마다 과거 이력 전체 재검증을 끼워 넣지 않는다. O(1)/실시간 성능은 주장하지 않는다.
