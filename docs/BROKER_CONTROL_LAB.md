# 호출 예산·미확정 주문 대조 실험실

2026-09-23 · DEV-D02 · 로컬 합성 `TEST_ONLY` 전용

## 현재 제공하는 것

공유 호출 예산, 우선순위, 주문 결과의 불확실성과 DB 복구를 **실제 통신 없이** 검사하는 개발용 모듈이다. 기존 [키움 순차 로그 모형](KIWOOM_COLLECTION_MODEL.md)을 대체하거나 실제 키움 수집기에 연결하지 않는다. 그 모형의 한계였던 대기 큐·진행 중 요청·공유 한도·영속 복구를 별도 계약으로 검증한다.

- [스케줄러](../src/core/broker-control.ts): 순수 상태 전이. 네트워크 요청을 보내지 않는다.
- [대조기](../src/core/broker-reconciliation.ts): 합성 주문/체결/포지션 증거를 검증하고 기존 `applyOrderEvent`로 수량·예약·비용 원장에 반영한다.
- [실험실](../src/server/broker-control-lab.ts): 기존 SQLite `Repository`의 한 트랜잭션에서 예산·주문·원장을 함께 저장한다.

UI 버튼, 서버 경로, API 인증/주문 어댑터, 장중 수집 기능은 추가하지 않았다. 이 모듈의 주문은 기존 엔진에서 준비한 합성 주문뿐이다. `networkRequests=0`, `liveEnabled=false`이며 엔진 상태는 계속 `RECONCILING`이다. 제어 큐의 명시적 `READY`는 실제 자동매매 재개나 보호주문 확인을 뜻하지 않는다.

## 실행과 정상 결과

프로젝트 루트에서 PowerShell로 실행한다. 기존 설치를 사용하며 새 패키지는 필요 없다. 매니페스트는 Node `>=24.20.0 <25`, npm `>=11 <12`; 이번 검증 환경은 Node24.20.0/npm11.19.0이다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/broker-control.test.js dist/runtime/tests/broker-control-review.test.js dist/runtime/tests/broker-reconciliation.test.js dist/runtime/tests/broker-control-lab.test.js dist/runtime/tests/broker-control-crash.test.js
```

기대 결과는 모든 테스트 통과, 실패·취소·건너뜀0이다. 시험은 메모리 DB 또는 새 임시 시험 DB만 사용한다. 강제 종료 시험은 시험이 직접 만든 자식 프로세스에만 적용한다. 생성한 임시 DB를 사용자 DB로 사용하거나 시험 자식 스크립트에 기존 DB 경로를 전달하지 않는다.

원본·전체 회귀·정적 검사는 기존 명령을 사용한다.

```powershell
npm run verify:originals
npm run lint
npm run format:check
npm test
npm run build
```

실제 실행 횟수·결과·실패 원인·인수 상태는 [PROGRESS · 공개 요약](PROJECT_STATUS.md)의 DEV-D02 기록이 최종 근거다. 이 안내에 명령이 있다는 사실 자체가 통과 기록은 아니다.

## 호출 계약과 포기 순서

설정은 실제 계좌/키가 아닌 `sim-...` 별칭과 `SYNTHETIC` 환경만 사용한다. 각 route에는 제공자·계좌·키·시장·TR이 있고, 제공자/계좌/키/TR 네 차원의 모든 해당 규칙을 동시에 만족해야 한다. 시장·풀을 나눠도 제공자/계좌 한도는 공유한다. 다른 제공자의 예산은 분리한다.

| 우선순위 | 합성 요청 | 경합 시 처리 |
| --- | --- | --- |
| Tier0 | 청산·취소, 안전 판단용 주문/체결/포지션 조회 | 아직 보내지 않은 요청 중 우선 선택. 한도·대상 주문 검사를 우회하지 않음 |
| Tier1 | 보유 감시·일상 계좌 동기화·보유 위험 뉴스 | 탐색보다 우선. 슬롯/예산을 못 얻으면 수동 확인 경고 |
| Tier2 | 신규 진입·후보 호가 | PAUSED·오래된 정보·안전 예산 부족에서 보류 |
| Tier3 | 탐색·과거 차트·일반 뉴스 | 대기 큐/보존 용량의 안전 몫을 사용할 수 없음 |

같은 Tier는 마감 → 대기 시각 → ID 순서다. 우선순위는 미전송 선택 순서일 뿐 전송 중 HTTP나 시장 주문을 취소하는 선점이 아니다. 제공자·환경·KR/US·안전/일반 슬롯을 구분하며, 모든 풀을 합친 최대치는 route 수와 lane 상한으로 제한된다. 실제 HTTP 연결 풀·스레드/OS 자원 격리는 구현하지 않았다.

### 예산·기록·안전 조회 예약

각 규칙은 rolling window 용량과 실행 전체 발송 상한, 일반 요청이 쓸 수 없는 안전 여유를 가진다. 새 ENTRY는 자기 발송1회와 이후 `ORDER_QUERY/FILL_QUERY/POSITION_QUERY` 각1회의 여유를 **동시에** 확보해야 한다. 세 조회는 원 ENTRY의 주문 ID 및 열린 대조 case와 결합한다. 다른 case에 예약을 넘길 수 없다.

발송 시에만 소비량이 늘어난다. 실패·429·타임아웃·재접속·재시작 때문에 소비 이력이나 미사용 조회 예약을 환급하지 않는다. 동일 ID의 동일 요청은 멱등이며 다른 내용은 거절한다. 동일 주문·동일 쓰기 동작의 전송 이력이 있으면 다른 요청 ID로도 재발송하지 않는다. ENTRY/EXIT와 CANCEL은 서로 다른 동작이지만 미확정 상태에서는 모두 보류한다. 이미 종결된 주문의 오래된 대기 쓰기 요청은 발송 직전에 폐기한다.

시험 설정의 대표값은 용량8/1초, 안전 여유3, 전체 발송80, 큐12, 보존 요청120, 풀당 슬롯1이다. 경계 시험은 용량4 또는 lane2 등을 별도로 지정한다. **모두 가상 시험값이며 키움 실제 한도·안전 상수·새 거래 정책이 아니다.** 스키마상 최대 route16, 규칙64, 큐128, 보존 요청500, case20, 증거 내 체결100으로 제한한다. 오래된 기록을 지워 같은 실행의 총 예산을 다시 쓰지 않는다. 보존 상한에 닿으면 새 실행으로 자동 초기화하지 않고 중단/진단해야 한다.

영속 감사 로그는 기존 Repository를 사용한다. 위 상한은 논리 상태/요청 크기 상한이지 전체 디스크·CPU·OS 메모리 사용량의 강제 할당량이 아니다. 디스크 쓰기 실패의 원자적 롤백을 시험했지만 운영용 보관·정리·디스크 예약 정책은 후속 운영 검증 사항이다.

## 실패와 복구

| 사건 | 유지하는 상태와 필요한 행동 |
| --- | --- |
| 429 | 호출 소비 유지. 해당 공유 규칙 모두에 `max(Retry-After, 최소 backoff)` 적용. 자동 무한 재시도 없음 |
| 읽기 실패 | 실패/전송 종료 확인 후 새 ID의 명시 재시도만 허용. 다시 예산 부과, 최대 재시도 수 제한 |
| 쓰기 응답 성공/실패 | HTTP 결과만으로 체결·취소 확정 금지. UNKNOWN과 주문 대조 필요 |
| 타임아웃 | 쓰기는 UNKNOWN, 읽기는 ERROR. 전송 슬롯은 실제 종료 증거 없이 반환하지 않음 |
| 조회 기간 누락·상충 | 주문/포지션/장부는 유지. case 보류·경고, 자동 재발주/재개 없음 |
| 프로세스 재시작 | DB의 소비량·주문/원장·예약 보존, 연결 epoch 증가, 이전 응답/증거 사용 차단. 미전송 진입/탐색 폐기 |
| 늦은 HTTP | 확정된 주문 대조 결과를 다시 UNKNOWN으로 낮추지 않음. 429 등 통신 경고/대기는 별도 유지 |
| 안전 슬롯/예산/마감 부족 | `SAFETY_UNAVAILABLE_MANUAL_REVIEW` 등 경고. 성공을 가장하지 않고 신규 노출 보류 |

작업자는 최신 DB 상태에서 직렬화한다. 두 작업자가 오래된 복사본으로 예산을 이중 소비하지 못하게 하며, 동시 writer lease와 fencing을 기존 Repository로 검사한다. 소유 시험 자식의 종료 후 미완료 전송은 종료된 로컬 연결로 처리하지만 주문 결과가 확정된 것으로 처리하지 않는다.

가상 시계의 단조성만 검사하며 실제 시계 동기화는 확인하지 않는다. 호가2초·계좌5초·FX60초 정책은 원본을 그대로 참조한다. 3초 된 호가로 신규 진입을 허용하지 않는다.

fixed/sliding/leaky 서버 오라클과 지연 편차 시험은 로컬 규칙이 서버 성공을 보장하지 못한다는 반례다. 송신800/1134/1468/1802ms와 편도 지연200/50/50/50ms가 서버의 한 fixed window에 네 요청을 도착시키는 사례도 포함한다. 키움 서버 알고리즘이나 실측 지연을 확인했다는 뜻이 아니다.

## 세 자료를 맞춰야 주문을 확정한다

대조 대상은 하나의 BOT 주문과 격리된 종목 노출이다. 같은 종목의 다른 보유 또는 같은 포지션의 다른 미종결 주문이 있으면 보류한다. 매수와 매도 모두 `UNKNOWN/CANCEL_UNKNOWN`을 취급하며, 미체결 BUY처럼 아직 포지션이 없는 경우도 포함한다. 일반 계좌의 다중 수동 거래까지 자동 배분하는 대조기는 아니다.

1. 현재 연결 세대에서 성공한 서로 다른 주문조회·체결내역·포지션 조회를 요구한다. case·시장·제공자·계좌 범위와 요청 동작을 확인한다.
2. 세 증거의 공통 `asOf`, 완결 표시, 주문 제출부터의 조회 기간, 응답 가용시각을 대조한다. 주문/결합된 전송보다 이른 증거, 미래·5초 초과 증거는 사용하지 않는다.
3. 체결 ID의 완전 중복은 한 번만 계산한다. 같은 ID의 다른 내용, 이미 반영한 체결 이력의 변경/누락, 누적 수량/가치 역행·한도 위반을 거절한다.
4. 주문 누적 체결과 체결 목록 합계, 기존 로컬 체결과의 차이, 포지션 수량 증가/감소가 모두 같아야 기존 체결 이벤트를 적용한다. 기존 수수료와 예약 계산을 재사용한다.
5. 부분 체결만 확인되면 잔여 주문은 UNKNOWN을 유지한다. 종결을 확인해도 큐/엔진을 자동 재개하지 않는다. 원 쓰기 요청 객체는 수정하지 않고 case의 원 요청 ID 결합으로 확인된 전송만 해소한다.

입력은 엄격한 스키마를 먼저 통과해야 감사 로그에 기록된다. 키/URL/인증 필드는 지원하지 않는다. 임의 실제 자료를 이 합성 계약에 넣는 것은 금지다. 이 검사는 공급자 진본 인증, 브로커 체결 ID 정정 처리나 실제 API에서 같은 cutoff의 완결 스냅샷을 얻을 수 있다는 증명이 아니다. 실제 어댑터는 페이지·체결 정정·조회 시점·계좌 범위를 검증해야 하며 완결 증거가 불가능하면 계속 보류해야 한다.

## 경고를 보았을 때

현재 시험에서는 실패 로그·남은 주문/보유·소비 예산과 경고를 조사하고 수정된 시험을 다시 실행한다. UNKNOWN을 정상 상태로 덮거나 기존 DB/기록을 지워 재개하지 않는다. 실제 운영의 수동 HTS/MTS 확인·연락·취소 절차는 별도 승인 및 실계좌 기능 검증에서 작성할 사항이다. 이 모듈이 대신 계좌 주문을 보내지는 않는다.

## 남은 검증과 다음 단계

미검증: 실제 키움 인증/한도·네트워크 지연·웹소켓·페이지 완결성·동일 계좌의 타 프로그램 호출, 실제 보호주문/OCO·모의/실계좌 주문, 전원/OS 장애 전체, 투자 성과. 웹 화면·HTTP 계약을 바꾸지 않았으므로 웹 E2E는 이번 인수 범위 밖이다. 외부 패키지 내부나 전체 OS 네트워크 차단을 정적 의존성 검사로 증명하지 않는다.

기존 G1 HOLD·G2 NOT_RUN·LIVE 잠금과 원본 정책은 유지한다. 현재 API 키 발급은 필요 없다. 다음 작업 후보는 [DEV-D03](DEVELOPMENT_EXECUTION_GUIDE_v1.md)의 **비례/최소/구간별 거래비용과 운영비 연결**이며, 이번에 착수하지 않았다.
