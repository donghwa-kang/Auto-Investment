## 🔧 제품 변경

### 자동 롤백 시 원인 보존

[Repository](../src/server/repository.ts)의 세 트랜잭션 경계가 공통 `rollback`을 사용한다. 활성 트랜잭션일 때만 `ROLLBACK`을 실행하고 원래 오류를 다시 던진다. 롤백 자체도 실패하면 두 오류와 원래 원인을 `AggregateError`에 보존한다. 자동 재시도·주문·재개는 추가하지 않았다.

시험은 임시 DB의 `max_page_count`를 현재 페이지 수+16으로 제한하고 마감 STATE 쓰기 후1MiB BLOB 삽입으로 실제 SQLite `errcode=13`을 발생시킨다. 수정 전에는 `cannot rollback - no transaction is active`/`errcode=1`로 덮였다. 수정 후 원오류 보존·트랜잭션 종료·장부/명령/감사/lease 원복, 제한 해제 후 같은 요청의 성공·중복 재시도를 검사한다. 물리 디스크 전체를 채우는 시험은 아니다.

### 포화 원문 입력 조기 거절

[Store](../src/server/cost-reservation-store.ts)는 스키마·소유권 확인 뒤 같은 쓰기 잠금 안에서 요청이 `POST_CLOSE_INPUT`이고 명령ID가 미등록이며 후속 입력100개가 이미 저장된 경우만 전체 재생 전에 거절한다.

이 경로는 **거절만** 하며 캐시를 근거로 금융 상태를 승인하지 않는다. 기존 ID·정상 수용·읽기·영수증 회수는 전체 이력/해시 검증을 유지한다. reducer의100개 한도도 그대로다. 초과 오류는 기존 `POST_CLOSE_INPUT_LIMIT`이며 DB/WAL·장부에 쓰지 않고 원문을 버리거나 덮어쓰지 않는다. 호출자가 미수용 원문을 보존해야 한다.

정책/계약 해시·스키마·의존성·거래 수치·100개/8,192 UTF-8 bytes 한도는 바꾸지 않았다. 구형 DB 이관이나 외부 엔드포인트도 없다.

신규 [시험](../tests/cost-finalization-hardening.test.ts)과 [자식 fixture](../scripts/cost-finalization-contention-fixture.mjs)를 사용한다.

| FH-06, 2개 | acquire/구형 transact의 자동 롤백 | 원인 보존·실패 후 성공 복구 |

FH-01은 운영비 예약 후 인식을 수행하여 예약 상계도 대조한다. PAY는 이미 인식된 의무의 지급이며 비용을 재인식하지 않는다. FH-03의 최대 적재는 빈 합성 계좌의 마감 조건이다. 거래/미지급이 있는 후속 원문은 기존 CF-12와 FH-01 RAW에서 별도로 검사한다. 재시작 후 한도 유지, 캐시 변조 시 읽기/기존 영수증 거절도 검사한다.

FH-04는 OWNER가 STATE 직후 쓰기 잠금을 가진 동안 CONTENDER의 소유권 취득이 `SQLITE_BUSY`로 실패하는 것을 확인한다. 같은/변조 마감 요청은 OWNER의 IPC 큐에서 처리된다. 이후 시험 시계상 lease 만료 후 CONTENDER가 새 epoch를 취득해 직접 원래/변조 마감을 호출하고, 구 OWNER 재시도는 `FENCED_WRITER`로 거절한다. 두 유효 writer의 동시 쓰기를 허용하지 않는다. 소수 IPC 요청/시험 시계의 경계 검사이지 대규모 분산 서버 처리량 시험은 아니다.

수정 전 빈 계좌에서 초과12회 거절은 약6,562ms, 최초 수정 후 집중 검사에서 초과128회는 약908ms였다. 두 실행 모두 거절 중 DB2,551,808bytes/WAL4,766,872bytes가 증가하지 않았다. Windows/Node24.20.0 단일 실행 관측이며 호출 수·동시 부하가 달라 벤치마크나 지연 보장이 아니다. 원문 합계819,200bytes는 전체 DB/WAL 크기와 다르다.

## 🔐 복구 규칙과 미검증

1. 발송 전에 원래 `closeId`, request 전체(`asOf`·manifest 포함), 명령ID·expectedState를 보존한다.
2. 응답 누락을 실패로 단정해 새 마감을 만들지 않는다. 소유권·저장소를 정상 복구한 뒤 원래 요청을 재전송한다.
3. 동일 요청이면 원래 receipt, 변조면 충돌이다. `current`의 후속 RECONCILING/HOLD는 유지되므로 영수증을 신규 승인으로 사용하지 않는다.
4. 자원 부족·경합·fencing 원인을 해결하지 않은 무한 재시도는 하지 않는다. 미수용 원문은 호출자가 보존한다.

FH-05는 부모가 원래 요청을 메모리에 보존하고 실제 COMMIT 후 서버 자식의 업무 응답만 누락시키는 IPC 시험이다. 시험용 완료 표식에는 금융 상태/영수증이 없다. 영속 outbox·HTTP 클라이언트·클라이언트 동시 재시작·실제 네트워크 단절 처리는 구현하거나 검증하지 않았다.

intake는 내부 개발자 메서드다.100개는 실행 하나의 저장 한도이며 전체 디렉터리 할당량, 다중 실행/파일 생성 남용, 요청률/동시성 제한, 장기 읽기에 따른 WAL 상한은 미구현·미검증이다. 조기 거절로 운영 전체의 DoS 방어까지 완성했다고 해석하지 않는다.

실제 시장/브로커/API·계좌·주문·물리 전원 차단·하드웨어 I/O 장애·OS 격리·장기 성능·수익성은 미검증이다. 손실 한도 보장을 제공하지 않는다.
