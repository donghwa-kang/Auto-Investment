# 분석 부모 프로세스 격리 — 방식 결정과 변경 명세

2026-09-14 설계 결정. **오프라인 검증용 우선 후보는 Windows LPAC + Job Object**입니다. 분석 부모를 처음부터 제한된 프로세스로 생성하고, 자식 명령에만 적용되는 Codex 권한과 구분합니다. 이번 결과는 설계 문서이며 실행기·OS 설정·실제 Codex 연결을 구현하거나 적용하지 않았습니다.

LPAC는 권한을 더 줄인 AppContainer입니다. Windows 보안 기능을 이용하지만 아래 실행기와 검증 절차는 이 프로젝트의 제안입니다. Codex 공식 지원 조합이나 이 PC에서 작동이 확인된 구성이라고 주장하지 않습니다. **전체 격리 구조는 선택했지만 실제 Codex의 기동·설정 분리 호환성은 미확정**입니다.

2026-09-15 후속: [OS 변경 없는 준비 CLI](ANALYSIS_LAUNCH_PREPARATION.md)에 이어 [C++ 요청 검증기](ANALYSIS_NATIVE_VALIDATOR.md)를 오프라인 빌드하고 고정 stdio 계약·거절·호스트 해시 결합을 시험했습니다. 검증기 자체의 일반 프로세스 실행이며 아래 실제 OS 실행기/권한 적용·파일 접근 probe는 여전히 미구현입니다. 실제 제한 실행은 별도 승인입니다. 아래 절차는 설계 당시 기록입니다.

## 1. 선택 근거와 제외한 방식

권한 준비 후속: [권한 검토·복구 판단](ANALYSIS_PERMISSION_PREPARATION.md)은 첫 고정 파일 시험에 필요한 16개 대상·보안 설명자와 복구 조건을 구체화합니다. scratch는 지정 파일 추가 쓰기만, 미사용 profile은 호스트 전용으로 제한합니다. 기존 거래 기준의 변경이 아니며 실제 권한 적용·프로필 저장소 생성/삭제·격리 성공을 뜻하지 않습니다.

영속 기록 후속: [잠긴 ACL 어댑터·디스크 시험 기록](ANALYSIS_PERMISSION_JOURNAL.md)은 실제 권한 적용/원복 코드의 빌드와 모형 사전/사후 기록·프로세스 종료 보류를 제공합니다. 실제 OS–저널 연결과 프로필 저장소/소유 증명은 남아 있으며 Windows 권한이나 기본 웹 앱 설정을 변경하지 않습니다.

최신 구현: [파일 접근 시험기·잠긴 격리 실행 코어](ANALYSIS_FILE_PROBE.md)에 일반 프로세스의 실제 더미 연산과 LPAC/Job 백엔드 코드를 추가했습니다. 실행 순서/실패·정리는 모형으로만 시험했으며 실제 Win32 격리 실행·프로필/ACL 적용은 하지 않았습니다. 아래 설계의 완료/미완료 여부는 후속 안내의 범위와 함께 읽어야 합니다.

| 방식 | 이번 결정 | 이유와 한계 |
| --- | --- | --- |
| 기존 Node 모형 제한 | 유지 | 고정 자체 모형용. 악성 코드/실제 에이전트의 OS 경계가 아님 |
| Codex native elevated만 사용 | 외부 경계로는 채택하지 않음 | 명령 경계만으로 부모 파일 API·비격리 실행 API를 보호했다고 볼 수 없음. 계정/방화벽/로그온 정책 변경도 필요 |
| Windows VM형 Sandbox | 현재 PC의 후보 제외 | 관측한 Core/Home는 공식 지원 대상이 아님. OS 업그레이드 구매를 전제하지 않음 |
| WSL2/별도 VM | 예비 대안 | 설치·배포판·가상화 미확인. 공유 경로/호스트 상호운용/통신 분리와 설치 승인이 추가로 필요 |
| LPAC로 부모 전체 시작 | 오프라인 실험의 우선 후보 | 고유 SID·명시 권한·프로세스 시작 속성으로 제한 설계 가능. 런타임 의존성/기존 ACL/관리 정책에 따른 실제 효력은 시험 필요 |

Codex 공식 문서의 `process/*`와 `thread/shellCommand`는 Codex 명령 샌드박스 밖에서 실행됩니다. `fs/*`는 절대 경로 API입니다. 일부 메서드를 중계하지 않는 것만으로 서버 내부 동작까지 제한했다고 취급하지 않습니다. [OpenAI App Server](https://learn.chatgpt.com/docs/app-server).

저장된 설치 버전 스키마도 experimental `ProcessSpawnParams`에 비격리 실행을, basic `ThreadShellCommandParams.command`에 스레드 sandbox 정책을 상속하지 않는 동작을 선언합니다. 선언을 확인했을 뿐 API를 호출하지 않았습니다. 이전 [스키마 관측](ANALYSIS_DUMMY_LAB.md#로컬-codex-스키마-관측)의 읽기 범위 필드 차이도 유지합니다.

네이티브 elevated의 변경 범위는 [OpenAI Windows 설명](https://learn.chatgpt.com/docs/windows/windows-sandbox), VM형 Home 미지원은 [Microsoft Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)에 근거합니다. 이전 elevated 우선 조사는 역사적 후보 검토로 남기며 자동 설정/약한 모드 fallback은 하지 않습니다.

## 2. 보호 경계와 데이터 흐름

```text
기존 모의매매 서버 / 장부 / 거래 정책 ── 변경·연결 없음

전용 시험 제어기(신뢰 영역)
  ├─ 새 더미 자료·변경 명세·실행 전후 증거 보관
  ├─ 고정 실행기: 승인된 경로/코드/설정 해시만 수용
  └─ 제한된 stdio ──> LPAC + Job 안의 검사 부모
                       ├─ 허용: 지정 더미 입력 읽기, 전용 임시 상태
                       └─ 금지: 보호 대상·호스트 설정·통신·추가 자식
       <── 해시/오류/결과만 ── 출력 검증기(외부에서 대조)

후속 별도 검증: 검사 부모 → 실제 Codex App Server로 교체
               자동 승격이 아니며 재검증·별도 승인 필요
```

신뢰 영역은 고정 코드·로컬 실행 사용자·OS입니다. 공격 대상으로 보는 것은 자료에 섞인 지시, 분석 프로세스의 오작동/침해, 잘못된 RPC와 자식 생성입니다. 관리자/커널 침해·악성 호스트 제어기·동일 사용자에 의한 증거 전면 교체까지 방어하는 구조는 아닙니다. 파일 해시는 서명이나 독립 OS 증명이 아닙니다.

제어기는 자식이 보낸 파일 경로·셸 명령·URL을 대신 실행하지 않습니다. stdout/stderr는 제한된 결과 데이터일 뿐 실행 지시가 아닙니다. 거래 DB·정책 파일·브라우저 세션·인증 핸들을 전달하지 않습니다. 실제 보호 대상 대신 같은 접근 형태를 재현하는 **새 더미 파일만** 시험합니다.

## 3. 예정 변경 목록 — 아직 적용하지 않음

`<run-id>`는 새 UUID, `<32hex>`는 같은 UUID의 하이픈 없는 소문자 32자리입니다. 아래는 대상 생성 규칙이지 배포 명령/기존 경로가 아닙니다. 실행 승인 화면에는 해소한 절대 경로·SID·해시·이전/예정 권한을 표시해야 합니다. OS 반환 경로는 아직 없으므로 현재 “정확한 적용 대상 확인 완료”로 표시하지 않습니다.

| 변경 대상 | 제안 내용 | 영향 및 복구 원칙 |
| --- | --- | --- |
| 새 시험 루트 | `work/analysis-os-lab/run-<run-id>/`만 생성. 기존 폴더면 중단 | 소유 증거 보존. 프로젝트 루트/기존 work 전체 ACL 변경·삭제 금지 |
| 전용 AppContainer 프로필 | `PaperLab.Analysis.Offline.v1.<32hex>` 1개. 기존 이름 재사용 금지 | 새 로그인 계정은 아님. OS가 현재 사용자용 폴더/레지스트리 저장소를 만들 수 있음. 별도 생성/정리 승인 필요 |
| `bin/` | 해시 고정 검사 PE/필수 의존성 복사본만. SID에 읽기·실행 | 원래 설치 폴더/시스템 DLL ACL을 수정하지 않음. 임의 프로그램 허용으로 확장 금지 |
| `input/` | 허용 읽기용 더미 입력. SID에 읽기만 | 쓰기·삭제·이름 변경·권한 변경 금지. 내용/실효 ACL 전후 대조 |
| `private/` | 비허용 읽기/쓰기/설정 canary. SID/capability에 접근 허용 없음 | 새 fixture의 상속된 광범위 권한 제거 여부 명세화. 실제 파일 연산으로 거절 확인 |
| `scratch/`, `profile/` | 비밀값 없는 임시 쓰기 범위. 필요할 때만 낮은 무결성 라벨과 한정 권한 | 입력·보고서와 분리. AppContainer 기본 저장소도 쓰기 가능 범위로 관측. 디스크 쓰기 전부 금지라고 표현하지 않음 |
| `evidence/` | 제어기만 기록. 컨테이너에 쓰기 권한/핸들 없음 | 자체 보고와 외부 증거 분리. 보관 후 명시적 정리만 허용 |
| 일회 Job·stdio·토큰 | 해당 검사 프로세스만 소속, 종료 시 닫음 | 기존 Codex/Node/사용자 서버를 이름으로 찾아 종료하지 않음 |
| 사용자/전역 설정·서비스·방화벽 | 변경 없음 | Codex 설정/인증, PATH, OS 사용자·그룹·로그온 권한, 방화벽/loopback 예외, WSL/가상화 설치 제외 |

AppContainer 프로필 생성은 사용자별 폴더와 레지스트리 저장소를 만드는 **실제 OS 변경**입니다. `CreateAppContainerProfile` 반환 SID를 기록하고 공식 API로 저장소 경로를 해소합니다. `ERROR_ALREADY_EXISTS`는 재사용하지 않고 중단합니다. 거절을 관리자 자동 승격으로 해결하지 않습니다. [Microsoft 생성 API](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile).

ACL은 이번에 새로 만든 대상만 수정합니다. 부모 경로 접근이 부족하면 전체 사용자/프로젝트 루트에 권한을 추가하지 않고 실패로 남깁니다. 링크·재분석 지점·다중 hardlink·경로 교체를 검사하고, 실행 파일과 입력은 쓰기/삭제 공유를 허용하지 않는 검증된 핸들로 고정하는 구현이 필요합니다. private ACL을 확인하지 않은 채 “추가 권한을 주지 않았다”는 사실만으로 차단을 단정하지 않습니다.

## 4. 실행기 구현 계약

아래는 **후속 오프라인 네이티브 시험기** 제안입니다. 현재 제품 명령이 아니며 임의 경로/프로그램을 받는 범용 실행기를 추가하지 않습니다.

1. TypeScript 제어기는 엄격한 요청·새 run-id·고정 시험 종류·파일/코드/설정 해시를 검증합니다. Win32 호출은 작은 네이티브 보조 실행기로 분리합니다. 셸 없이 숨김 실행하며 임의 argv·명령 문자열·외부 URL 입력을 받지 않습니다.
2. `SECURITY_CAPABILITIES`에 이번 SID와 capability 0개를 지정합니다. `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY`의 opt-out으로 LPAC를 요청하고 실제 토큰의 AppContainer SID·LPAC·capability·무결성을 확인합니다. 일반 AppContainer로 자동 fallback하지 않으며 네트워크/COM/광범위 파일·레지스트리 capability도 추가하지 않습니다. [Microsoft LPAC 구성](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer).
3. 명시 핸들 목록에는 stdio pipe 끝만 포함합니다. 해당 목록 사용 시 필요한 `bInheritHandles`와 핸들 상속 속성을 함께 검증하고 나머지는 비상속으로 유지합니다. 파일/소켓/Job/호스트 프로세스 핸들을 전달하지 않습니다. 자식 생성 금지 속성도 설정합니다. [Microsoft 시작 속성](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).
4. 일시 정지 상태로 생성하고 Job 소속·토큰·제한을 확인한 뒤 재개합니다. 시작 시 Job 지정 또는 재개 전 배정을 사용하며 기존 호스트 Job 제약과 충돌하면 중단합니다. breakaway는 허용하지 않습니다. [Microsoft Job 배정](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject).
5. 첫 네이티브 더미 실험은 활성 프로세스 1개, Job commit 메모리 128MiB, 사용자 CPU 시간 2초, 외부 wall-clock 10초, 출력 합계 8KiB를 제안합니다. 투자 위험 수치/Codex 운영 한도가 아닙니다. Job 마지막 핸들 닫기 시 종료하고 시간/출력 초과는 실패입니다. commit 한도를 RSS 보장으로 표시하지 않습니다. [Microsoft Job 제한](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).
6. 네트워크 capability·loopback 예외를 부여하지 않습니다. 실제 TCP/UDP/DNS/IPv4/IPv6·localhost·호스트 서비스 접근은 별도 양성 대조가 있어야 검증됩니다. 통신 실패만으로 OS 차단 합격으로 세지 않습니다. 디스크/커널 자원 전체의 DoS 방어를 이 수치로 보장하지 않습니다.

Codex는 보조 프로세스/추가 시스템 자원을 요구할 수 있습니다. 이 구성에서 시작하지 못하면 **호환 실패**이며 제한을 자동 완화하지 않습니다. 의존성/추가 실행 파일을 확인해 새 명세/승인을 받아야 합니다. LPAC 자체가 명령 문자열별 허용 목록을 제공하는 것도 아닙니다.

## 5. 설정·인증 분리 계약

새 cwd나 권한 프로필 이름만으로 사용자 설정이 배제되지 않습니다. 공식 설정 계층은 CLI·프로젝트·선택 프로필·사용자·관리 기본값 등을 병합하며 프로젝트 비신뢰도 사용자/전역 설정까지 배제하지 않습니다. 관리 requirements는 별도 강제 조건입니다. [OpenAI 설정 계층](https://learn.chatgpt.com/docs/config-file/config-basic).

분리 목표는 기존 설정 복사/수정이 아니라, 접근 가능한 설정·상태를 새 시험 범위로 한정하고 유효 설정과 출처를 검사하는 것입니다.

- 첫 네이티브 시험은 Codex를 시작하지 않아 Codex 설정이 필요 없습니다. 새 시험 명세만 사용합니다.
- 후속 Codex 기동 시험의 후보는 OS API에 넘기는 새 자식 환경 블록에서 `USERPROFILE`·`APPDATA`·`LOCALAPPDATA`를 전용 profile 하위로 한정하는 방식입니다. 현재 프로세스/전역 환경을 수정하지 않고 기존 HOME·CODEX_HOME·PATH·토큰·프록시·플러그인 환경을 상속하지 않습니다. TEMP/TMP는 전용 scratch, 시스템 경로는 검증된 최소값만 전달하는 설계입니다.
- 이는 홈 해석의 **미검증 가설**입니다. 알려진 폴더 API·HKCU·관리 설정·실행 파일 상대 경로를 쓸 수도 있습니다. 환경 변수만 바꿔 분리됐다고 세지 않습니다. 기존 설정 접근은 LPAC 경계에서 금지하고, 실패를 없애려고 실제 개인 홈/인증 파일을 열어주지 않습니다.
- 유효 설정은 새 설정 canary·필수 필드/출처의 최소 보고로 검증합니다. 사용자 설정 원문/비밀값 전체 덤프는 금지합니다. 필수 관리 정책을 읽을 수 없거나 적용 여부가 불명확하면 중단하며 더미 requirements로 기존 제한을 우회하지 않습니다.
- 로컬 명세에 없는 읽기 필드·실험적 named profile 필드를 무작정 넣지 않습니다. 실행 검증 전 TOML/인자를 작동하는 예제로 제공하지 않습니다. `dangerFullAccess`/`externalSandbox`로 기동 오류를 회피하지 않습니다.
- 실제 로그인·모델 통신은 별도 설계/승인입니다. 오프라인 통신 금지와 모델 통신 허용은 같은 프로필이 아닙니다. 기존 인증 토큰 추출/복사·API 키 전용 경로는 만들지 않습니다.

**설정 분리의 방식/실패 조건은 정했지만 설치된 Codex의 정확한 홈 해석·실효 설정 계약은 실행 검증 전까지 미확정**입니다. 이를 숨기고 실제 연결을 활성화하지 않습니다.

## 6. RPC 경계와 검사 도구 보완

미래 제품 연결기는 상태별 허용 메서드를 열거합니다. 최소 초기화·1회 분석·결과·취소 흐름 외에 `process/*`, `thread/shellCommand`, `fs/*`, 설정 쓰기·setup·로그인·플러그인/앱/MCP 관리·임의 명령 전달은 중계하지 않습니다. 알 수 없는 메서드/버전·미승인 도구 요청은 실행하지 않고 종료합니다. 내부 도구가 같은 RPC를 거친다는 가정은 하지 않습니다.

OS 시험은 **별도 고정 시험기**로 부모 수준 접근을 확인해야 합니다. 제품 메서드 거절 테스트와 혼동하지 않습니다. 실제 App Server의 파일/비격리 실행 API로 새 canary에 접근하는 시험은 LPAC 경계가 먼저 확인된 이후 별도 승인 범위입니다.

기존 [더미 자기검사기](ANALYSIS_DUMMY_LAB.md)는 같은 폴더/manifest/파일 사전검증을 신뢰합니다. 그대로 감싸면 비허용 경로 사전검사 실패를 실제 연산 거절과 혼동할 수 있습니다. 새 OS probe는 **호스트가 fixture 진위·양성 대조를 확인하고 제한된 부모가 고정 대상 연산 자체를 시도**하도록 분리해야 합니다. 임의 사용자 파일/명령은 받지 않습니다. 거절 코드나 자식 passed 값 하나로 격리 완료를 승인하지 않습니다.

첫 파일 시험은 허용 입력 읽기·임시 상태 쓰기 양성 대조, private 읽기·write-only 열기/추가·생성·삭제·이름 변경 음성 대조, 토큰/Job/핸들·부모 종료 확인입니다. 성공해도 [기존 10종 OS 수용 기준](ANALYSIS_ISOLATION_READINESS.md#더미-검증-절차와-합격-조건) 전체를 대체하지 않습니다. 통신 수신기는 테스트 소유 대상으로만 만들고 현재 4173/4184 사용자 서버에 시험 트래픽을 보내지 않습니다.

## 7. 승인과 복구

실행 전 승인 묶음은 새 run 절대 경로, 코드/명세 해시, 고유 프로필 이름/예정 SID, 공식 API가 관리할 저장소 범위, 새 파일 ACL/무결성 변경, 시험 종류·시간/자원 한도, 정리 대상입니다. **프로필 생성은 프로젝트 밖 OS 저장소 변경도 포함한다**고 표시해야 합니다. API 반환 후 예상 밖 경로/상태가 발견되면 실행을 중단하고 해당 리소스만 기록합니다.

복구는 이번 Job 종료 → 소속 프로세스 종료/핸들 닫힘 확인 → 외부 evidence 보존 → 소유 프로필/새 대상만 정리 순서입니다. 이름만 일치하는 기존 리소스를 삭제하지 않습니다. 생성 성공/소유 기록·SID·최종 절대 경로·기존 객체 부재 근거가 없으면 자동 삭제를 보류합니다.

`DeleteAppContainerProfile`은 열린 핸들이 남으면 저장소를 완전히 지우지 못할 수 있고 없는 프로필에도 성공을 반환합니다. 반환 코드만으로 복구 완료를 판단하지 않고 실제 상태를 재확인합니다. 실패 시 잔여 범위를 보고하며 전체 레지스트리/Packages 폴더 삭제로 해결하지 않습니다. [Microsoft 삭제 API](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile).

기본 보관은 evidence와 새 시험 결과 유지입니다. 승인된 정리만 수행하고 제거 내용/복구 가능 여부를 보고합니다. 현재 아무 프로필·ACL·Job도 생성/변경/삭제하지 않았으므로 복구할 OS 변경이 없습니다.

## 8. 다음 구현 단위와 완료 조건

**다음은 OS 변경 없는 전용 실행기/변경 명세의 준비 구현**입니다. 네이티브 빌드 도구를 읽기 전용으로 확인하고 명세 생성·경로/해시/범위 검증·기본 실행 잠금·잘못된 입력 거절을 먼저 만듭니다. 프로필 생성/실제 제한 실행은 자동 수행하지 않습니다.

이번 제한적 조회에서 PATH의 dotnet.exe, 고정 SDK 폴더의 8.0.204, Windows Kits Include 폴더 존재를 관측했습니다. PATH에서 cl.exe/clang.exe는 발견하지 못했습니다. C++ 컴파일러 미설치 확정이나 SDK 빌드 성공을 뜻하지 않습니다. 실행·restore·설치는 하지 않았습니다. 네이티브 빌드 체인은 실제 경로/버전/오프라인 빌드로 확인해야 합니다.

준비 구현 뒤 구체 대상과 부작용이 표시된 별도 승인을 받아 파일 전용 OS 실험을 수행합니다. 이후 부모 API·설정 분리·통신·종료 수용 시험을 확장합니다. 실제 인증/모델 승인과 거래 연결은 그 후에도 별개입니다. 외부 설치/OS 업그레이드·전역 변경이 필요하면 자동 확대하지 않습니다.

현재 미검증: LPAC 생성/권한/통신·Home 실제 동작, 필수 시스템 읽기 목록·빌드 체인, Codex 기동/설정/관리 요구·인증/모델·사용량, 모든 우회/복구·실시장 성과. 기존 모의매매·학습 기준과 원본 37파일은 변경하지 않습니다. 선택형 보조 분석 준비이지 전체 시장 매매 기능 또는 수익성 검증의 완성이 아닙니다.
