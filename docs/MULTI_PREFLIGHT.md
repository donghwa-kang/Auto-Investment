# 오프라인 다종목 통합 사전점검

2026-09-13. 카탈로그 분류·상품 정보 보강·시장 자료 품질 검사를 **원본 TEST_ONLY 입력에서 다시 실행**하고, 같은 종목·버전·시점의 자료인지 연결 검사하는 독립 명령이다. 저장된 성공 플래그를 이어 붙이지 않는다. 시험 통과는 투자 추천·전략 준비·주문 승인이 아니며 실제 조회·웹 UI·사용자 모의매매 엔진과 연결하지 않았다.

## 빠른 실행

후속 [오프라인 차트 신호 재생](SIGNAL_REPLAY.md)은 이 검사의 원본 입력을 각 시점에 재실행하고 별도 전체 이력을 요구한다. 이 명령 자체가 전략/주문을 실행하도록 변경된 것은 아니다.

기존 의존성이 설치된 프로젝트 루트의 PowerShell에서 실행한다. 공통 환경/설치는 [README](../README.md)를 따른다. 추가 패키지·키·웹 서버가 필요하지 않다.

```powershell
npm run build:engine
npm run market:preflight -- fixtures/multi-preflight-v1.json
```

정상 출력은 `OFFLINE_MULTI_PREFLIGHT_COMPLETE`, `status=HAS_BLOCKS`다. 일부 실패를 포함한 시험이므로 HAS_BLOCKS가 이 샘플의 예상 결과다.

| 샘플 집계 | 수 | 의미 |
| --- | ---: | --- |
| 현재 카탈로그 항목 | 8 | 시험 종목 6개와 벤치마크 2개 |
| 통합 통과 | 4 | 시험 종목 2개 + 벤치마크 2개 |
| 상품 제외 | 1 | 사용자 제외 범위의 단일종목 레버리지 시험 값 |
| 보류 | 3 | 상품 정보 결측, 호가 잔량 0, 시장 자료/연결 누락 |
| 시험 종목 후보 | 2 | `KR:TEST-KR`, `US:TEST-US`. 벤치마크는 후보에 포함하지 않음 |

[샘플](../fixtures/multi-preflight-v1.json)은 현재 상품 8개·보강 근거 2개·시장 대상 7개·시장 자료 31개·연결 7개다. 출처·상품 속성·시각·시세·달력·기업행동/벤치마크는 합성 가정이다. 원문 해시의 0 반복도 시험 표지이지 실제 발행사 문서를 확인한 값이 아니다. KR/US에 같은 시험 시각을 사용한 것은 실제 동시 개장을 뜻하지 않는다.

결과는 매번 새 `data/multi-preflight-checks/시각-UUID.json`으로 저장한다. 지정한 시험 입력은 읽기만 하고, 기존 개별 검사 결과·사용자 모의 DB·일회용 코드는 읽거나 덮어쓰지 않는다. 웹 화면에는 아직 표시하지 않는다.

## 구조와 입력

[입력 스키마](../src/core/multi-preflight-schema.ts), [순수 통합 검사기](../src/core/multi-preflight.ts), [독립 CLI](../src/server/multi-preflight-cli.ts)로 책임을 분리했다. 기존 개별 검사기를 변경하지 않고 재사용하며 ID별 Map으로 연결과 벤치마크 관계를 조회한다. 실시간 처리량이나 대규모 성능 SLA를 측정한 것은 아니다.

| 필드 | 계약 |
| --- | --- |
| `schemaVersion`, `purpose` | `OFFLINE_MULTI_PREFLIGHT_V1`, `TEST_ONLY`만 허용 |
| `asOf` | 시간대 포함 ISO 시각, 최대 밀리초 정밀도. UTC로 정규화 |
| `enrichment` | [상품 정보 보강 입력](CATALOG_ENRICHMENT.md) 전체. 안에 원본 `catalog` 포함 |
| `market` | [시장 자료 품질 입력](MARKET_DATA_QUALITY.md) 전체 또는 null. null은 자료 없음으로 보류하며 조회로 대체하지 않음 |
| `bindings` | 최대 128개 명시적 연결. 빈 배열은 가능하지만 미연결 상품/시장 대상은 보류·진단 |

추가 필드·캐시된 `stageReports`·임의 `approved` 플래그·실자료 모드·잘못된 하위 스키마는 입력 전체를 거절한다. 원본 카탈로그 최대 50,000행·시장 대상 최대 64개 등 하위 자원 제한도 유지하며, CLI 파일 상한은 합친 JSON 전체 16 MiB다. 전체 카탈로그를 시장 자료 대상 수에 맞춰 임의 절단하지 않는다. 현재 보이는 상품에 필요한 연결/자료가 없으면 그 항목은 남겨 보류한다.

루트 `asOf`, `enrichment.catalog.asOf`, `market.asOf`는 정규화 후 같아야 한다. 다르면 검사를 시작하기 전에 `MULTI_PREFLIGHT_AS_OF_MISMATCH`로 전체 거절한다. 최신 자료를 과거 시점으로 소급하거나 한 단계의 시각을 자동 수정하지 않는다. 현재 컴퓨터 시각이나 실제 장중 여부를 검사하는 명령은 아니다.

## 연결 계약

각 연결에 다음 필드가 필요하다. 해시는 모두 소문자 64자리 16진수 또는 null이며 null은 통합 보류다.

| 필드 | 확인 대상 |
| --- | --- |
| `assetKey` | 시장 품질 입력의 대상 키 |
| `market`, `instrumentId` | 현재 카탈로그의 시장+종목 ID 키. 심볼 검색으로 대체하지 않음 |
| `baseRecordHash` | 정규화된 현재 원본 카탈로그 기록 전체 해시 |
| `enrichedItemHash` | 해당 상품의 현재 보강 결과 항목 전체 해시. 사실·근거·상태·원본 해시 포함 |
| `qualityAssetHash` | 정규화된 시장 대상 계약 전체 해시. 식별·역할·출처·벤치마크 키·세션·시간 창·기업행동 가정 포함 |

해시는 기존 `hash` 함수를 사용한다. `baseRecordHash`는 `classifyCatalog(...).items[].recordHash`, `enrichedItemHash`는 `hash(enrichCatalog(...).items[]의 해당 항목)`, `qualityAssetHash`는 `hash(parseMarketQuality(...).assets[]의 해당 항목)`에 대응한다. 파일 바이트·심볼 문자열의 해시가 아니다. 샘플에는 계산된 시험 연결이 들어 있다.

연결 확인 후에도 시장 대상의 ID·시장·거래소·심볼·통화를 현재 상품 정보와 별도로 대조한다. 거래소/통화 결측이 정당하게 보강됐으면 보강된 사실을 사용한다. 해시를 다시 계산해 붙였더라도 다른 종목·잘못된 자료가 통과하지 않는다.

통합 검사는 연결 해시를 자동으로 고쳐주지 않는다. 원본 기록·근거·대상 계약이 정정되면 이전 연결이 무효가 될 수 있다. 그 변경의 의미와 대응 관계를 확인한 새 시험 입력을 명시적으로 만들어야 한다. 결과의 `actual` 값을 복사해 넣는 것만으로 자료 진위·상충·거래 자격 문제가 해결되지는 않는다.

완전히 같은 연결은 한 번 처리한다. 서로 다른 연결이 같은 시장 대상을 가리키거나 여러 시장 대상이 같은 상품을 가리키면 관련 상품을 보류한다. 없는 현재 상품·없는 시장 대상·미연결 시장 대상은 `bindingIssues`에도 남긴다. 새 상품을 심볼만으로 자동 편입하거나 가장 먼저 읽힌 연결을 선택하지 않는다.

## 검사와 보류 전파

1. 공통 형식·시점을 확인하고 기존 카탈로그 분류, 상품 보강, 시장 품질 검사를 실행한다. 개별 단계가 정상인지 직접 확인할 수 있도록 상세 결과도 남긴다.
2. 원본 또는 보강 단계가 `EXCLUDED`이면 최종 상품 제외를 유지한다. 좋은 시세로 해제하지 않는다. 추가 결측/상충이 있으면 그 사유도 함께 기록한다.
3. 원본의 단순 결측이 유효한 시험 근거로 보강되어 해결됐으면 다음 검사가 가능하다. 원본 상태는 기록에 보존한다. 보강 후에도 남은 만료·식별 상충·상품 결측을 무시하지 않는다.
4. 일대일 연결, 세 연결 해시, 현재 상품과 시장 대상의 식별을 확인한다. 시세 품질 보류도 최종 보류로 전파한다. 필요한 연결/자료가 없으면 통과하지 않는다.
5. INSTRUMENT가 지정한 벤치마크도 상품·연결·시세 품질 통합 검사를 통과해야 한다. 같은 벤치마크를 공유하는 여러 종목에 결과를 전파하며 순서에 의존하지 않는다.
6. 모든 조건을 만족한 INSTRUMENT만 `testCandidates`에 기록한다. BENCHMARK 통과는 집계에는 포함되지만 시험 종목 후보에는 포함하지 않는다.

벤치마크도 이번 좁은 시험 계약에서는 카탈로그의 주식/ETF 상품 분류를 거친다. 독립 지수 전용 자료 계약·실제 대용 ETF 적합성·상관 검증은 제공하지 않는다. 이 시험의 보수적 연결 조건을 실제 벤치마크 선정 정책으로 승계하지 않는다.

한 종목의 자료 오류가 관계없는 모든 종목을 자동 탈락시키지는 않는다. 다만 동일 식별 상충·공유 벤치마크 등 관계가 있으면 전파한다. 연결되지 않은 자료 문제가 있어 `HAS_BLOCKS`인 결과에도 영향받지 않은 시험 후보가 존재할 수 있다. 어느 경우에도 주문이나 다음 실행을 자동 시작하지 않는다.

미래 상품·보강 근거·시세 정정은 기존 검사기의 기준 시점 규칙으로 배제한다. 순서·완전 중복·현재 판단에 무관한 행을 바꾸더라도 동일 판단을 재현한다. 반면 연결/대상 계약 자체를 바꾸는 것은 명시적인 시험 범위 변경이며 판단 해시도 달라질 수 있다.

## 결과 읽기

| 구분 | 의미 |
| --- | --- |
| 항목 `TEST_PREFLIGHT_PASS` | 해당 시험 상품/연결/요구 시간 창 통과. 전략·주문 승인이 아님 |
| 항목 `EXCLUDED` | 원본/보강 분류에서 제외. 시세가 정상이더라도 유지 |
| 항목 `BLOCKED` | 누락·상충·잘못된 연결·시세·벤치마크 등의 미해결 문제 |
| 전체 `NO_TEST_CANDIDATES` | 통과한 INSTRUMENT가 0개. 빈 목록/전부 제외/전부 보류도 포함 |
| 전체 `HAS_BLOCKS` | 시험 후보가 있지만 일부 상품 또는 연결 문제가 남음 |
| 전체 `TEST_PREFLIGHT_COMPLETE` | 시험 후보가 있고 미해결 상품/연결 보류가 없음. 명시적 제외 항목은 있을 수 있음 |

`items[].stages`는 원본/보강/시장 품질의 실제 상태와 이유, `binding`과 `actual`은 요청/현재 연결 해시, `benchmarkCatalogKey`는 연결한 벤치마크를 보여준다. 보강기와 통합기는 현재 상품을 기준으로 동작하며 상품별 보류를 숨기기 위해 항목을 삭제하지 않는다. 시장 자료 검사는 보류/제외 상품에 대해서도 시험 입력 범위에서 실행될 수 있다. 그 단계의 정상 결과가 통합 허가를 의미하지 않는다.

`stageReports`는 재실행한 상세 결과, `stageDecisionHashes`는 단계별 판단 해시다. 통합 `decisionHash`는 단계 판단·연결 계약·종목별 결과·정책/연구 범위를 결합하고, `inputHash`는 정규화된 전체 입력을 결합한다. 상세 보고서의 미래/중복 진단과 입력 해시는 통합 판단 해시에서 분리한다. 이는 변경 추적 수단이며 발행사 인증·전자서명·제3자 진위 보증이 아니다.

항상 `realDataReady=false`, `strategyReady=false`, `strategyEvaluated=false`, `selectionPerformed=false`, `paperOrdersEnabled=false`, `liveEnabled=false`, `sourceAuthentication=UNVERIFIED_TEST_INPUT`을 유지한다. 후보 키는 정규 순서이지 수익·매력도 순위가 아니다.

## 실행·보안·검증 경계

PAPER/BACKTEST만 허용하며 `LIVE_ENABLED=true`는 거절한다. 새 환경변수·.env 자동 로딩·외부 키 설정은 없다. 공용 로컬 파일 읽기로 직접 URL/UNC/장치 경로, 과대 파일, 잘못된 UTF-8/JSON을 거절한다. 공용 읽기 오류에는 기존 `CATALOG_` 접두어가 사용된다. Windows 연결 지점/네트워크 드라이브·ACL·OS 네트워크 격리·디스크/전원 장애·암호화·백업은 보장하지 않는다. 신뢰하는 로컬 시험 파일만 사용한다.

인자 하나를 받고, 출력은 `wx`와 `0600` 요청으로 새 파일에만 쓴다. 품질 보류·제외·시험 후보 0개라도 검사/저장이 완료되면 종료 코드 0이다. 모드·인자·시점·정책·입력·저장 실패는 종료 코드 1이며 원문 오류·입력 비밀값을 출력하지 않는다. 자동 삭제·재실행·조회·승인 기능은 없다.

```powershell
npm run build:engine
node --test --test-concurrency=1 dist/runtime/tests/multi-preflight.test.js dist/runtime/tests/multi-preflight-cli.test.js
node work/verify-multi-preflight.mjs
```
